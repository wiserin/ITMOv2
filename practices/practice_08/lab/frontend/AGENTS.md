# Правила фронтенда AnimeMap

Применять вместе с `../agent-rules/`. Текущее задание разрешает
изменять существующий фронтенд и `../docs/frontend/`, заменяя старые
ограничения общего контекста. Backend и API-контракты не менять.

## Слои

- `src/UI/components/` — универсальные визуальные элементы.
- `src/UI/styles/` — палитра, семантические токены, reset и стили UI.
- `src/UI/index.ts` — публичный API универсальной библиотеки.
- `src/components/` — компоненты AnimeMap: аккаунты, бренд, меню,
  авторизация, иллюстрации. Используют UI через его публичный API.
- `src/styles/` — цвета иллюстраций, предметные стили, композиция
  экранов, адаптивность. Единственный импорт из `main.tsx` —
  `src/styles/index.css`, включающий стили UI.
- `src/pages/` и `App.tsx` — сценарии, состояние, маршрутизация, API.
- `src/api/` — транспортные модели и HTTP-клиент.

Зависимости: страницы → предметные компоненты → универсальный UI.
Страницы также могут напрямую использовать UI и API. UI не зависит
от приложения, аккаунтов, ролей, API, маршрутов и предметных стилей.
Внутри UI использовать прямые импорты соседних компонентов.

## Обязательное переиспользование

Перед созданием нового визуального элемента AI обязан проверить
`src/UI/index.ts` и каталог в `../docs/frontend/README.md`, найти
подходящий компонент и переиспользовать его.

Если универсального элемента нет, сначала добавить его в UI,
экспортировать, описать API и проверить поведение; затем использовать
в приложении. Если элемент предметный, добавить его в
`src/components/`, составляя из готовых UI-компонентов. Предметные
компоненты не экспортируются из UI. Один компонент — отдельный файл.
Структурный HTML, заголовки и текст допустимы в страницах. Не создавать
повторные реализации кнопок, полей, диалогов и других готовых элементов.

## Код и дизайн

- Строгий TypeScript, отступы 4 пробела; не использовать `any`.
- Сохранять стиль AnimeMap, композицию и зелёную палитру.
- Не добавлять сторонние UI-библиотеки и избыточные зависимости.
- Компоненты UI именуют классы `ui-*`, предметные стили — `am-*`.
  Не применять компонентные стили к глобальным `input` и `label`.
- Использовать ограниченные шкалы токенов. Семантические цвета
  ссылаются на базовую палитру; компоненты используют семантику.
- Новое значение сначала сопоставить существующей шкале.
  Точные размеры иллюстраций и композиции допускаются локально.
- Обеспечивать контраст обычного текста ≥4.5:1, важных визуальных
  индикаторов и фокуса ≥3:1. Декоративные исключения документировать.
- Сохранять имена элементов, связи label/hint/error, нативную
  валидацию, FormData, автозаполнение, клавиатуру, фокус и reduced motion.
- Формы защищать синхронным ref до первого await, освобождать в
  finally. Disabled/loading кнопки не заменяют эту защиту.
- Не имитировать серверный выход удалением локального состояния
  или HttpOnly cookie; не придумывать отсутствующие API-ручки.

## Проверки и документация

Обновлять `../docs/frontend/README.md`, при необходимости отчёты
регрессий и доступности рядом. Сохранять существующие проверки,
добавлять тесты видимого поведения в существующий Playwright.
Проверять фактическое число HTTP-запросов при повторной отправке.

Из `frontend/`:

```bash
npm run build
npm run typecheck
npm test
npm run test:e2e
```

Тестовая UI-страница собирается Vite во временный каталог через
Playwright global setup и не входит в production-сборку.
