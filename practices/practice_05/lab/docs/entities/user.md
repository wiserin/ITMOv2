# Пользователь (UserEntity)

## Назначение

Пользователь — самостоятельная доменная сущность AnimeMap API. С ней связаны пользовательское избранное и полномочия на выполнение операций в соответствии с RBAC.

Структура хранения описана в [`../database.dbml`](../database.dbml), таблица `users`. Этот документ описывает смысл полей, инварианты и правила доступа.

## Атрибуты

Доменная модель — `dataclass(slots=True, kw_only=True)`. ORM-модель в infrastructure отделена от доменной сущности и преобразуется в неё и обратно явно.

| Атрибут | Доменный тип | Назначение |
| --- | --- | --- |
| `id` | `UUID` | Идентификатор пользователя, UUIDv4 |
| `email` | `str` | Уникальный контактный email в каноническом виде |
| `username` | `str` | Обязательное имя пользователя |
| `display_name` | `str \| None` | Необязательное отображаемое имя; не является уникальным логином |
| `role` | `UserRole` | Одна текущая роль пользователя |
| `is_active` | `bool` | Возможность выполнять операции от имени пользователя |
| `created_at` | `datetime` | Время создания с часовым поясом |
| `updated_at` | `datetime` | Время последнего изменения с часовым поясом |

## Инварианты

1. UUIDv4 создаётся в domain до сохранения пользователя. Получение идентификатора не требует `flush()`; серверного default генерации ID нет.
2. Email обязателен, не пуст и уникален. Перед сохранением применяется нормализация `trim + lowercase`. Максимальная длина — 254 символа.
3. Отображаемое имя необязательно. Если задано, оно не может состоять только из пробелов; максимальная длина — 100 символов.
4. У пользователя ровно одна роль из `UserRole`. Неизвестный код или строковое значение отклоняется без подстановки роли по умолчанию.
5. Новый пользователь получает роль `user` (`1`). Клиент не выбирает роль при регистрации.
6. Изменение роли и `is_active` — отдельные административные операции. Обычное редактирование профиля не позволяет менять эти поля.
7. При `is_active = false` запрещены все операции от имени пользователя независимо от его роли.
8. `updated_at` не может быть раньше `created_at`. При изменении записи приложение обновляет `updated_at`; SQL `DEFAULT now()` действует только при вставке.
9. Управление избранным требует проверки владельца для всех ролей. Роль администратора сама по себе не предоставляет доступ к чужому избранному.
10. `username` обязателен, не пуст и не состоит только из пробелов. Перед сохранением удаляются пробелы по краям; максимальная длина — 100 символов. Уникальность и регистронезависимость пока не определены. Для входа в текущем presentation-контракте используется email.

## Пароли пользователя

Пользователь связан с [`Credential`](credential.md) отношением один-ко-многим: каждая запись хранит хэш одного пароля. В `User` хэши не хранятся.

У пользователя не может быть больше одного текущего credential. После установки пароля существует ровно один текущий credential; при смене пароля прежняя запись сохраняется как историческая. Установка и смена пароля выполняются транзакционно по правилам `Credential`.

Уникальность email обеспечивается ограничением БД; доменная проверка формата email не подменяется SQL-проверкой нормализации.

## Сессии пользователя

Пользователь связан с [`SessionEntity`](session.md) отношением один-ко-многим. В MVP каждая сессия представлена одним JWT в Secure HttpOnly cookie со скользящим сроком жизни; ограничения на количество сессий пока нет. При проверке сессии учитываются актуальная активность пользователя и его текущая роль. Процесс входа и авторизации описан в [`../auth.md`](../auth.md).

## Bootstrap-аккаунт

Первая миграция создаёт активного пользователя с `username = root`, `email = root@example.com`, отображаемым именем `root` и ролью `admin` (`3`). Начальный пароль — `root`; в `CredentialEntity` сохраняется только Argon2id-хэш, запись отмечена текущей.

Это явное исключение из обычного назначения роли `user` при регистрации. Bootstrap создаётся один раз на пустой схеме, не создаёт сессию и не сбрасывает данные аккаунта при последующих запусках или повторном `upgrade head`.

## Роли и права (RBAC)

| Код в БД / domain | Строка в presentation | Права активного пользователя |
| --- | --- | --- |
| `1` | `user` | Поиск локаций, получение координат и статуса верификации; просмотр, добавление и удаление собственного избранного |
| `2` | `moderator` | Все права `user`; верификация координат и модерация локаций |
| `3` | `admin` | Все права `moderator`; назначение ролей, блокировка и разблокировка пользователей |

- Каталог ролей и соответствие ролей правам фиксируются явной политикой в domain/application. Отдельные таблицы `roles`, `permissions`, `user_roles` для этой модели не требуются.
- Числовой код роли — идентификатор, а не уровень доступа. Проверки вида `role >= required_role` не используются.
- Права модератора не включают управление пользователями и ролями.
- Числовые коды задаются явно, не перенумеровываются и не переиспользуются.

## Представление роли между слоями

- В domain используется `UserRole` на основе `IntEnum`; в БД — `integer`.
- В presentation используются строки `user`, `moderator`, `admin` с явным преобразованием в обе стороны.
- Общий базовый класс доменных `IntEnum` может предоставлять маппинг без зависимости domain от FastAPI/Pydantic.
- Строковое представление — стабильный контракт API; стандартный `str(IntEnum)` не заменяет этот маппинг.

## Открытые вопросы

- Пароли и секреты сессий хэшируются Argon2id. Параметры стоимости хэширования и внешние идентичности ещё предстоит согласовать.
- Анонимный доступ, конкретные статусы модерации и детальные политики административных операций ещё предстоит определить.
