# Пароль пользователя (Credential)

## Назначение

Credential хранит хэш пароля конкретного пользователя. Связь с [`User`](user.md) — многие-к-одному: у пользователя может быть история паролей, но только один текущий пароль.

Структура хранения описана в [`../database.dbml`](../database.dbml), таблица `credentials`.

## Атрибуты

Доменная модель — `dataclass(slots=True)`. ORM-модель и маппинг находятся в infrastructure.

| Атрибут | Доменный тип | Назначение |
| --- | --- | --- |
| `id` | `UUID` | UUIDv4 записи, создаваемый в domain до сохранения |
| `user_id` | `UUID` | Идентификатор владельца пароля |
| `password_hash` | `str` | Argon2id-хэш пароля с солью и параметрами алгоритма |
| `is_current` | `bool` | Является ли пароль текущим |
| `created_at` | `datetime` | Время создания с часовым поясом |

## Инварианты

1. Credential принадлежит ровно одному существующему пользователю. Владелец записи не меняется.
2. Хранится только хэш; исходный пароль не сохраняется. Хэш не включается в публичные ответы API или логи.
3. `password_hash` обязателен и не пуст. Используется тяжёлый алгоритм Argon2id с индивидуальной солью. SQL-проверка непустого значения не заменяет проверку формата хэша в приложении.
4. У пользователя одновременно не более одного credential с `is_current = true`. При наличии установленного пароля текущий credential должен быть ровно один.
5. Исторические записи с `is_current = false` не используются для аутентификации.
6. При смене пароля создаётся новая запись. Хэш старого пароля не перезаписывается; предыдущий credential перестаёт быть текущим.
7. Установка первого пароля создаёт текущую запись; до установки пароля пользователь может не иметь credentials.
8. Физическое удаление пользователя каскадно удаляет его credentials. Блокировка пользователя через `is_active` историю паролей не удаляет и не разрешает вход даже с текущим паролем.

## Транзакционность и конкурентные изменения

- Установка и смена пароля выполняются одной транзакцией.
- Для сериализации параллельных изменений блокируется строка владельца в `users` через `SELECT ... FOR UPDATE`. Это работает и при установке первого пароля, когда credentials ещё нет.
- При смене сначала прежняя запись переводится в `is_current = false`, затем вставляется новая с `is_current = true`. Изменения должны попасть в БД именно в этом порядке, поскольку уникальный индекс проверяется немедленно.
- При ошибке транзакция целиком откатывается: пользователь не должен потерять прежний текущий пароль из-за неудачной смены.
- Частичный уникальный индекс по `user_id WHERE is_current = true` обеспечивает на уровне PostgreSQL ограничение «не более одного». Наличие текущей записи после установки пароля обеспечивается прикладным сценарием, а не этим индексом.
- В DBML индекс объявлен в `indexes` с `unique` и `note: 'Partial index: WHERE is_current = true'`. При реализации миграции предикат необходимо задать явно: примечание DBML само по себе не создаёт SQL-условие.

## Аутентификация

При входе используется только текущий пароль. Успешный вход создаёт отдельную [`Session`](session.md) и один JWT bearer-токен. Процесс описан в [`../auth.md`](../auth.md).

## Открытые вопросы

- Параметры стоимости Argon2id.
- Политика сложности паролей, срок хранения истории и запрет повторного использования паролей.
- Проверки полномочий при смене и сбросе пароля, влияние на активные сессии.
