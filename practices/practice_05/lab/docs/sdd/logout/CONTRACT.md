# AnimeMap — общий контракт Logout V1

**Версия:** 1.0  
**Дата:** 2026-11-02  
**Статус:** окончательный общий контракт на основании утверждённых пользователем ADR-01–ADR-11.  
**Этап SDD:** вход для подготовки согласованных спецификаций Frontend V2 и Backend V2; разрешения генерировать код или начинать реализацию нет.

## 1. Назначение, приоритет и термины

Контракт завершает только предъявленную серверную сессию AnimeMap. Он не добавляет logout всех устройств, управление сессиями, refresh-токены, JWT blacklist, новые хранилища или cross-origin deployment.

Основания: [REVIEW.md §6–10](REVIEW.md), исторические [UI V1](UI_SPEC_V1.md), [Backend V1](BACKEND_SPEC_V1.md), baseline [auth](../../auth.md), [errors](../../errors.md), [Session](../../entities/session.md), [User](../../entities/user.md) и `agent-rules/`.

При расхождении с независимыми V1 применяется этот контракт. V1 сохраняются как история. Обычные Auth/RBAC и остальные endpoints сохраняют baseline; единственное относящееся к активности исключение — право неактивного владельца закрыть собственную сессию (§3).

«Должен», «только», «запрещено» — нормативные требования будущей реализации. Наличие текста не означает наличия кода или выполненных проверок.

- **Предъявленная сессия:** запись, выбранная по `jti` JWT из `session_token` конкретного запроса, после проверки JWT и секрета.
- **Пригодная для Logout сессия:** запись существует, владелец существует, `closed_at IS NULL`, `now < expires_at`, JWT и secret подтверждены. `is_active` владельца не ограничивает Logout.
- **Logout-401:** отказ проверки credential/состояния именно Logout, не инфраструктурная или proxy-аутентификация.
- **Сохранить cookie:** не отправлять устанавливающий/удаляющий `Set-Cookie` для `session_token` в этом ответе. Это не обещание неизменности хранилища при других параллельных ответах.
- **Поколение авторизации:** идентификатор текущего локального auth-контекста. Его замена/очистка инвалидирует старые callback.
- **Клиентская попытка:** локальная операция с уникальным ID и конечным ожиданием; её завершение не доказывает завершение операции FastAPI/PostgreSQL.

## 2. Публичный HTTP-запрос и границы proxy

### 2.1. Запрос

```http
POST /v1/auth/logout HTTP/1.1
Cookie: session_token=<jwt>
X-AnimeMap-Logout: 1
```

1. Путь ровно `/v1/auth/logout`, метод POST; ID пользователя/сессии в path отсутствуют. Имя backend-маршрута `auth_logout`, группа OpenAPI `auth`.
2. Тело содержит ноль байт. `{}`, `null`, пробел, произвольный JSON и повреждённый JSON — непустое тело и дают `400` после успешной CSRF-проверки. Любые query-параметры, включая параметры с пустым значением, дают `400`.
3. Пустое тело допустимо с Content-Type или без него; JSON-парсинг не является условием успешного Logout.
4. Заголовок `X-AnimeMap-Logout` должен иметь значение `1`. Отсутствующее, другое или неоднозначное множественное значение даёт `403`. Имя HTTP-заголовка регистронезависимо.
5. Браузер использует относительный URL своего origin, `credentials: 'same-origin'`, `cache: 'no-store'`. JWT не читается JavaScript, не хранится в localStorage/sessionStorage и не отправляется в Authorization.
6. Корректный Bearer без cookie не аутентифицирует Logout. Query/body не могут выбрать другую сессию даже при известном её ID.

### 2.2. Топология и ответственность Node.js proxy

Единственная топология V1: **Browser → same-origin Node.js proxy → FastAPI**. Рабочая браузерная проверка Secure cookie проводится по HTTPS. Отдельная CORS/credentialed cross-origin схема не поддерживается.

Proxy должен:

- распознавать Logout и пропускать POST на тот же путь API;
- проверять присутствующий Origin POST по полной нормализованной тройке **scheme, hostname, effective port** публичного origin; различие схемы, hostname либо порта означает `403 / access_denied`. Некорректный Origin, в том числе `null`, не совпадает;
- определять публичную схему из доверенной конфигурации/транспорта, а не из произвольного клиентского `X-Forwarded-Proto`; конкретный способ настройки остаётся в инфраструктуре команды;
- сохранять baseline: отсутствие Origin само по себе не заменяет и не отменяет обязательную проверку CSRF-заголовка; оно не является подтверждением доверия;
- передавать клиентские Cookie и `X-AnimeMap-Logout`, не добавлять отсутствующий заголовок и не исправлять неверное значение;
- не отбрасывать/обнулять body или query перед их проверкой, превращая недопустимый запрос в допустимый;
- передавать статусы, Set-Cookie, Cache-Control и Allow без потери семантики. У `204` не добавлять JSON-тело;
- не следовать redirect API. Неожиданный `3xx` Logout преобразуется в контролируемый `502` без применения его Set-Cookie; преобразование регистрации `303→201` не применяется;
- выдавать контролируемые ошибки маршрута в формате §4, включая ошибки Origin, метода, upstream-связи и timeout;
- использовать upstream timeout **15 000 мс** от запуска upstream-запроса до завершения чтения ответа. До этого завершения успешный ответ не должен быть отправлен браузеру;
- при истечении upstream-бюджета возвращать `504`, если браузерное соединение ещё доступно; другая ошибка upstream-соединения даёт `502`. Эти ответы не являются Logout-401 и не удаляют cookie.

CSRF и сессия повторно проверяются в FastAPI Presentation независимо от того, какие проверки выполнены proxy. Proxy не должен подменять результат backend-валидации успехом.

### 2.3. Методы и приоритет проверок

На распознанном Logout-пути GET и остальные неподдерживаемые методы возвращают `405 Method Not Allowed` без проверки сессии, изменения БД и удаления cookie. Ответ содержит `Allow: POST`. Для HEAD действуют HTTP-правила отсутствия тела; содержимое ошибок остальных методов соответствует §4. OPTIONS не открывает cross-origin доступ, не аутентифицирует и не изменяет сессию.

Для POST порядок наблюдаемых отказов:

1. Присутствующий недопустимый Origin может быть отклонён proxy с `403` до API.
2. Отсутствующий/неверный CSRF-заголовок → `403`, независимо от тела/query/cookie.
3. Непустое тело или query-параметры → `400`, независимо от cookie.
4. Только после этих проверок проверяются cookie, JWT и состояние сессии.

Следовательно, POST без CSRF и с непустым телом даёт `403`, с корректным CSRF и непустым телом без cookie — `400`, с корректным пустым запросом без cookie — `401`. Отклонение метода/Origin/CSRF/формы запроса не изменяет сессию. Проверки формы нельзя обходить общим proxy-буфером, выдающим для распознанного непустого тела другой прикладной статус вместо `400`.

## 3. Порядок серверных операций и граница аутентификации

1. **Presentation:** выполнить проверки §2, извлечь `session_token`. При отсутствующей/пустой cookie — Logout-401.
2. **Application:** отдельный `LogoutUseCase(BaseUseCase)` с именованным методом `logout` принимает токен, не Request/Response. DI собирает зависимости; HTTP-коды, CSRF и cookie не входят в UseCase/Domain.
3. Проверить JWT существующим JwtProviderPort: фиксированный EdDSA/Ed25519, подпись, типы/структуру `jti`, `secret`, `iat`, UUIDv4. Новый `exp`, ротация или иной формат JWT не вводятся.
4. Прочитать сессию по `jti`, предварительно проверить существование/закрытие/истечение. Проверить secret по `secret_hash` существующим SecretManagerPort. Открытый секрет не попадает в сущность, репозиторий, БД или ответ. JWT decode и тяжёлый Argon2id не блокируют event loop; verify выполняется до row locks.
5. В одной общей PostgreSQL-транзакции взять блокировку **пользователя, затем сессии**. Перечитать актуальные строки, не сохранять старый ORM snapshot. Сверить принадлежность владельцу и неизменность проверенного secret_hash.
6. После получения блокировок повторно проверить существование пользователя/сессии, `closed_at`, срок по свежему timezone-aware UTC-времени. При `now >= expires_at` — `401`, без закрытия или продления.
7. **Исключение ADR-07:** `is_active=false` не запрещает эту операцию. Незакрытая, неистёкшая сессия с подтверждёнными JWT/секретом закрывается и при неактивном владельце. Обычный Auth, `/account/me` и иные защищённые ресурсы по-прежнему требуют активного пользователя. Logout не выдаёт UserDTO для дальнейшего доступа и не активирует пользователя.
8. Вызвать доменную команду закрытия и сохранить возвращённую сущность через SessionRepository. Закрытие задаёт `closed_at = max(now, last_used_at)`; повтор доменной команды сохраняет исходный `closed_at`. Не меняются id, user_id, secret_hash, created_at, last_used_at, expires_at; запись не удаляется.
9. Commit выполняется до отправки `204` и удаления cookie. Репозитории выполняют flush, commit/rollback принадлежат существующей фабрике сессий; `PostgresSessionDI` function-scope обеспечивает завершение транзакции до HTTP. Flush без commit недостаточен.
10. После подтверждённого commit Presentation формирует §5. На исключении незавершённая транзакция откатывается. Неизвестный результат commit из-за разрыва соединения возвращается как ошибка, без обещания rollback.

Запрещено вызывать обычные `AuthUseCase.authenticate()`, `AuthUseCaseDI` или `SessionEntity.use()` перед/внутри Logout. Успешный или неуспешный Logout не продлевает сессию. PostgreSQL — источник истины; Redis/blacklist для Logout не нужны. Собственные ошибки — существующие общие доменные исключения, перевод в HTTP — общий Presentation mapper.

## 4. Ответы ошибок

Все контролируемые ответы Logout и его proxy-маршрута имеют `Cache-Control: no-store`. Ошибки, допускающие тело по HTTP, используют JSON с Content-Type `application/json` (charset допустим):

```json
{
  "error": "authentication_failed",
  "message": "Authentication failed",
  "details": {"reason": "session_closed"}
}
```

`error` и `message` — строки, `details` — объект, в том числе пустой. Текст message не является основой клиентской логики. Токены, Cookie/Set-Cookie, secret/hash, сырые SQL/параметры и исключения не включаются в JSON или прикладное логирование.

| Условие после проверок более высокого приоритета | HTTP / error | details | Cookie |
|---|---|---|---|
| Неподдерживаемый метод | 405 / method_not_allowed | Объект; причина может уточняться | Сохранить |
| Присутствующий Origin не совпадает/некорректен | 403 / access_denied | `reason=origin_check_failed` | Сохранить |
| Нет/неверен CSRF-заголовок | 403 / access_denied | `reason=csrf_check_failed` | Сохранить |
| Непустое тело или query | 400 / bad_request | Объект с безопасным контекстом валидации | Сохранить |
| Нет/пуста cookie | 401 / authentication_failed | `reason=missing_session_cookie` | Удалить |
| Неверная подпись/алгоритм/claims JWT | 401 / authentication_failed | `reason=invalid_token` | Удалить |
| Отсутствует сессия/владелец | 401 / authentication_failed | `reason=session_not_found` | Удалить |
| Сессия закрыта | 401 / authentication_failed | `reason=session_closed` | Удалить |
| Сессия истекла | 401 / authentication_failed | `reason=session_expired` | Удалить |
| Неверный secret | 401 / authentication_failed | `reason=invalid_secret` | Удалить |
| Повреждён сохранённый Argon2-хэш | 400 / bad_request | По существующему mapper, без хэша | Сохранить |
| Недоступность PostgreSQL, в том числе при commit | 503 / service_unavailable | По существующему mapper | Сохранить |
| Прочая backend-ошибка | По docs/errors.md; для неожиданной внутренней ошибки 500 / internal_error | Без секретов; retryable/sqlstate по baseline, где применимо | Сохранить |
| Upstream timeout proxy | 504 / service_unavailable | `reason=upstream_timeout` | Сохранить |
| Upstream-связь недоступна/неожиданный redirect | 502 / service_unavailable | `reason=upstream_failure` | Сохранить |

При нескольких дефектах credential приоритет внутренних причин не является гарантией; возвращается первая обнаруженная. В изолированном сценарии с единственным дефектом применяется указанная причина. Неактивность владельца сама по себе **не** ошибка Logout и не даёт `inactive_user`.

Применять no-store и удаление на `401` нужно к фактическому ответу mapper, в том числе при исключении после подготовки handler-response. На ошибке commit подготовленный `204` должен быть заменён ошибкой без удаления cookie. Proxy не должен превращать инфраструктурный отказ в `401`.

UI должен обрабатывать корректный HTTP-статус даже при отсутствующем/невалидном JSON: `401` завершает локальный вход, остальные ошибки используют fallback §6. Без достоверного HTTP-ответа результат — сетевая ошибка. Неожиданные `200/201/202` не считаются успехом.

## 5. Успех, cookie и повтор

```http
HTTP/1.1 204 No Content
Cache-Control: no-store
Set-Cookie: session_token=; Path=/; Max-Age=0; Expires=Thu, 01 Jan 1970 00:00:00 GMT; Secure; HttpOnly; SameSite=Lax
```

1. Тело отсутствует: ни `{}`, ни `null`, ни JWT; Location/redirect не выдаются. Только точный статус `204` означает успешное закрытие этим запросом.
2. На `204` и каждом Logout-401 удаляется только `session_token`. Имя/Path=/ и host-only scope без Domain совпадают с login. Пустое значение, Max-Age=0, Expires в прошлом, Secure, HttpOnly и SameSite=Lax обязательны. Порядок атрибутов и кавычки пустого значения не значимы.
3. На `400/403/405/500/502/503/504` и других ошибках заголовок изменения `session_token` не отправляется. Proxy не генерирует cookie сам и сохраняет backend-команду удаления на 204/401.
4. `204` подтверждает сохранённое закрытие. Удаление cookie само по себе, Logout-401, уход со страницы и локальная очистка UI не подтверждают новую запись closed_at.
5. Повтор со старым JWT закрытой сессии даёт `401/session_closed`; после удаления cookie — `401/missing_session_cookie`. closed_at неизменен. HTTP-статусы различаются, серверный эффект идемпотентен.
6. Истёкшая сессия даёт `401`, closed_at не материализуется и срок не продлевается. Доменная идемпотентность не даёт публичному endpoint право считать такую сессию успешно закрытой.
7. После commit закрытия сохранённая копия JWT не проходит новую аутентификацию. Другие независимые сессии не изменяются. Доставка Set-Cookie и commit не атомарны; в сценариях гонок применяются §7–8.

## 6. UI state machine и приоритет событий

Состояние авторизации и занятость клиентской auth-операции — разные величины. Logout-попытка хранит ID и поколение, в котором начата; защищённые запросы также привязаны к поколению. Очистка/замена auth-контекста меняет поколение. Завершённая либо просроченная попытка не становится актуальной повторно.

| Текущее состояние | Событие | Следующее состояние / действие |
|---|---|---|
| authenticated/idle или authenticated/failed | Нажатие Logout, auth-операция свободна | pending; новая попытка; один POST; меню закрыто, видимое «Выходим…»; повтор и новые защищённые действия заблокированы |
| pending | Повторный клик/Enter, открытие меню, смена hash | Запрос не дублируется; hash не отменяет ожидание и блокировку |
| pending, поколение/ID актуальны | Точный 204 | signed-out; очистка auth-контекста и данных; #/login; «Вы вышли из аккаунта.» |
| pending, поколение/ID актуальны | Logout-401 | unauthenticated; очистка; #/login; «Сессия недействительна. Войдите снова»; без повтора Logout |
| pending, поколение/ID актуальны, авторизация сохранена | Иная ошибка, неожиданный 2xx, timeout | authenticated/failed; текущий экран и аккаунт сохранены без утверждения активности сессии; ошибка и ручной повтор; блокировка снята |
| authenticated/idle, failed или pending | 401 защищённого запроса актуального поколения | unauthenticated; очистка и #/login. Если Logout ещё ожидается, занятость auth-операции сохраняется до её клиентского завершения/timeout |
| Любое | Результат/ошибка/401 старого поколения или неактуальной Logout-попытки | Не меняет текущие auth-данные, маршрут, уведомления либо состояние новой попытки; завершение её собственного ожидания может освободить только её auth-операцию |
| authenticated/failed | Закрыть уведомление | authenticated/idle; аккаунт не восстанавливается из сохранённого snapshot |
| authenticated/failed | Ручной повтор, auth-операция свободна | pending с новым ID; старый ID не может завершить новую попытку |
| signed-out/unauthenticated, auth-операция свободна | Новый успешный login по baseline | Новое поколение, актуальный аккаунт, главная; данные/уведомления прежнего пользователя отсутствуют |

Если после стороннего 401 старый Logout завершится ошибкой или 204, очищенная авторизация не восстанавливается и старый результат не заменяет уведомления нового поколения. Login не запускается, пока ещё занята локальная auth-операция (§7).

Очищаются аккаунт, поиск/пагинация пользователей, выбранная карточка, личные ошибки и состояния в памяти. Защищённые экраны и Header скрываются одновременно с очисткой, без промежуточного кадра личных данных на login. Старые ответы не восстанавливают данные после выхода или входа другим пользователем.

### 6.1. Сообщения, восстановление и доступность

| Результат | Текст |
|---|---|
| 204 | «Вы вышли из аккаунта.» |
| Общий logout-401 | «Сессия недействительна. Войдите снова» |
| Сетевая ошибка, локальный status 0 | «Не удалось подтвердить выход: нет соединения. Попробуйте ещё раз.» |
| UI timeout или 504 | «Не удалось подтвердить выход: сервер не ответил вовремя. Попробуйте ещё раз.» |
| 502/503 | «Не удалось подтвердить выход: сервис временно недоступен. Попробуйте позже.» |
| 400/403 и другие ошибки/неожиданные ответы | «Не удалось подтвердить выход. Попробуйте ещё раз.» |

Ошибки Logout не используют текст о поиске пользователей, сырые message/details или секреты. В failed доступны «Повторить выход» и «Закрыть уведомление», ошибка не исчезает по таймеру. Успех/недействительность показываются на login, закрываются вручную и сбрасываются при новом входе. После 204 дополнительный /account/me для отображения login не требуется.

Back/Forward и защищённый hash не восстанавливают очищенные экраны. После перезагрузки действует baseline-проверка /account/me: 401 → вход; недоступность → экран ошибки загрузки с повтором. Закрытие вкладки/перезагрузка не считаются подтверждением Logout.

Кнопка Logout доступна мышью, касанием, Enter/Space; пометка «Скоро» отсутствует. Прогресс видим вне dropdown, имеет role=status и текст, занятость/недоступность объявляются вспомогательным технологиям. При запуске фокус возвращается на фокусируемый триггер меню, не разрешающий действия pending. Ошибка имеет role=alert, повтор/закрытие доступны клавиатурой. После перехода на login фокус на заголовке, итог — role=status. Узкий экран не обрезает сообщения/действия.

## 7. Сериализация и временные границы

1. В одной вкладке одновременно выполняется не более одной **клиентской** auth-операции login/logout. Повтор Logout или login во время незавершённого ожидания не отправляется и автоматически не ставится в очередь. Проверка аккаунта как часть baseline-login относится к той же клиентской login-операции.
2. Сторонний 401 может открыть login, но не освобождает занятую Logout-операцию. Управление отправкой login остаётся заблокированным до завершения её клиентского ожидания.
3. Upstream-бюджет proxy — 15 секунд (§2.2). UI начинает собственный бюджет **20 000 мс** при отправке Logout; он охватывает получение результата/чтение ответа. При более ранней ошибке proxy ждать 20 секунд не нужно.
4. Если за 20 секунд результата нет, UI завершает ожидание как failed (либо остаётся unauthenticated, если auth уже очищена), инвалидирует ID и освобождает локальную операцию. Поздний callback не меняет новое состояние. Отмена клиентского транспорта может использоваться, но не считается доказательством отмены сервера или невозможности позднего cookie-эффекта.
5. После завершения клиентской попытки пользователь может выполнить доступный ручной повтор или новый login. Это не утверждает, что старая операция PostgreSQL завершена. Вкладка не запускает два активных локальных ожидания, но серверное перекрытие после timeout возможно.
6. Автоматические повторы Logout запрещены в UI и proxy. details.retryable не запускает автоповтор. Новый POST — только по явному действию пользователя.
7. Разница 15/20 секунд — бюджет ожидания, а не гарантированная доставка 504: соединение browser/proxy тоже может зависнуть. Жёсткий срок завершения транзакции БД этим контрактом не задаётся.

**Граница доказательства:** игнорирование callback защищает состояние приложения, но браузер применяет Set-Cookie независимо. Поэтому после timeout не заявляется абсолютная защита cookie нового login, даже внутри вкладки, без отдельного технического доказательства. Между вкладками глобальная сериализация не требуется.

## 8. Конкурентные сценарии и гарантии

| Сценарий | Обязательный результат / принятая граница |
|---|---|
| Два Logout одной пригодной сессии; срок не истекает, хранилище исправно | Один commit/204; второй после перечитывания 401/session_closed; closed_at не перезаписывается |
| Auth коммитит продление первым | Logout закрывает актуальную продлённую запись, не откатывая её времён |
| Logout коммитит первым | Auth после блокировки видит closed_at, даёт 401, не продлевает |
| Срок наступил во время verify/ожидания locks | Повторная проверка даёт 401/session_expired; Logout ничего не закрывает и не продлевает |
| Владелец стал неактивным до финальной проверки | При остальных выполненных условиях Logout закрывает сессию, commit→204; доступ к ресурсам не появляется |
| Владелец удалён до финальной проверки | 401/session_not_found; Logout не подтверждает закрытие; каскадное удаление baseline не является записью Logout |
| Бизнес-запрос прошёл Auth до закрытия | Может завершиться после Logout; отмена/rollback его эффектов не обещаются |
| Commit выполнен, ответ потерян | Запись остаётся закрытой; UI не объявляет успех без ответа; повтор со старым JWT/без cookie даёт 401 и удаление |
| Разрыв при commit, подтверждение неизвестно | Ошибка без удаления cookie; нельзя обещать ни закрытие, ни rollback; повтор вручную |
| Login/Logout в одной вкладке до завершения ожидания | Второй auth-запрос не отправляется |
| Новый login после timeout; старый ответ запаздывает | Старый callback не меняет новое поколение UI; абсолютная сохранность новой cookie не гарантируется |
| Login другой вкладки конкурирует с Logout старой сессии | Позднее удаление одноимённой cookie может затронуть новый credential браузера; новая независимая серверная запись не закрывается этим Logout |
| Другая вкладка использовала общую закрытую сессию | При следующем защищённом 401 или перезагрузке очищает UI и показывает login. Мгновенный broadcast/polling не требуется |

## 9. Таблица ожидаемых результатов

Состояние UI предполагает актуальную попытку; устаревшие события всегда подчиняются §6. D = команда удаления cookie по §5; K = не менять cookie этим ответом; ? = доставка неизвестна.

## 11. Готовность команд и остановка до реализации

Frontend Team и Backend Team должны самостоятельно подготовить свои V2 по инструкциям REVIEW.md §9–10 и сопоставить их с требованиями и C-01–C-27 этого документа. Здесь V2 не создаются, исходные V1 не исправляются.

Согласованность считается документально подтверждённой, когда обе V2 ссылаются на этот контракт и не вводят иных HTTP-статусов, cookie-политик, правил неактивного владельца, таймаутов или более сильных гарантий конкуренции. Новое расхождение предъявляется на согласование, а не устраняется молчаливым изменением контракта.

Риски §7–8 приняты в V1. Противоречий между утверждёнными ADR нет; исключение ADR-07 из baseline явно зафиксировано в §1 и §3. Актуализация baseline/OpenAPI/agent-rules должна быть включена в план команды, но в текущей задаче не выполняется.
