### Baseline и целевые требования

Сохраняется установленный V1 контекст: Header содержит заглушку выхода,
App хранит аккаунт в памяти и проверяет `/v1/account/me`, API-клиент
обращается к `/v1` с same-origin credentials и no-store. README описывает
React/TypeScript, Node.js 22+ static server/proxy, HTTPS-настройки,
страницы login/register/home/account/admin и обработку защищённого `401`.
Наличие Logout в спецификации не означает, что он уже реализован.

Ранее открытые HTTP-вопросы V1 теперь закрыты Contract. JWT остаётся
только в серверной HttpOnly cookie; источником истины остаётся серверная
сессия. Для Logout действует узкое исключение: неактивный владелец
может закрыть собственную пригодную сессию, не получая доступа к другим
ресурсам. Baseline-запрет обычной аутентификации неактивного пользователя
сохраняется. **Основание изменения:** ADR-01, ADR-07, ADR-11; LOG-06;
Contract §1, §3.

Идентификаторы US-01–US-06 и AC-01–AC-16 сохранены из V1;
AC-17–AC-24 добавлены для уточнений контракта. Изменённые требования
снабжены LOG/ADR непосредственно в соответствующих разделах и таблицах.
Неизменённые требования доступности и продуктовые границы унаследованы
из V1. При новом противоречии требуется согласование, а не локальная
поправка архитектуры. **Основание:** Contract §11; REVIEW §9.

## 2. Цель и границы

Пользователь через существующую кнопку «Выйти» завершает только текущую
предъявленную сессию и видит понятный результат на экране входа.
Выход доступен с главной, аккаунта и Admin Panel; роли `user`,
`moderator`, `admin` имеют одинаковые условия Logout.

Сохраняются границы V1: нет logout всех устройств, refresh-токенов,
управления сессиями, JWT blacklist, новых хранилищ, автоматических
повторов и офлайн-успеха. Подтверждающий диалог не требуется.
Выход не меняет пароль, роль или активность аккаунта.

Единственная топология — Browser → same-origin Node.js proxy → FastAPI.
Отдельный cross-origin deployment и полная межвкладочная координация
не входят в объём. Сериализуются клиентские Login/Logout внутри одной
вкладки; это не обещание отсутствия серверного перекрытия после timeout.
Новая независимая серверная сессия не закрывается Logout старой, но
поздний ответ может удалить общую одноимённую browser-cookie.
**Уточнение V1:** LOG-02, LOG-03, LOG-09; ADR-03, ADR-05, ADR-10;
Contract §2, §7–8.

## 3. Пользовательские сценарии

### US-01 · Обычный выход — P1

**Как** вошедший пользователь, **я хочу** выбрать «Выйти», **чтобы**
завершить текущую сессию и освободить интерфейс для нового входа.

1. При свободной локальной auth-операции пользователь выбирает «Выйти».
2. Меню закрывается, видимо «Выходим…», создаётся одна Logout-попытка.
3. Отправляется `POST /v1/auth/logout`, без body/query, с
   `X-AnimeMap-Logout: 1`, same-origin credentials и no-store.
4. Только актуальный `204` переводит UI в `signed-out`: одновременно
   очищаются аккаунт и защищённые данные, скрываются Header и экраны,
   открывается `#/login`, показано «Вы вышли из аккаунта.».
5. Дополнительная проверка `/account/me` для показа входа не требуется.
   После освобождения auth-операции доступен новый baseline-login.

Пригодная сессия неактивного владельца также получает `204`; UI
не превращает этот результат в отказ из-за `is_active=false`.
**Изменение:** LOG-01, LOG-06, LOG-08; ADR-01, ADR-02, ADR-07, ADR-09,
ADR-11; Contract §2–6.

### US-02 · Сессия недействительна — P1

Актуальный Logout-`401` очищает auth-контекст и защищённые данные,
открывает `#/login`, переводит UI в `unauthenticated`. Точный общий текст:
**«Сессия недействительна. Войдите снова»**. Повтор Logout не предлагается.
Это не утверждение нового закрытия в БД. На каждом Logout-`401` сервер
отправляет удаление cookie, но JS не проверяет и не выполняет его сам.

Отсутствующая/пустая cookie, неверные JWT/secret, отсутствующая запись
или владелец, закрытие и истечение — `401`. Неактивность существующего
владельца сама по себе не является ошибкой Logout.
**Изменение:** LOG-05, LOG-06; ADR-04, ADR-07, ADR-11; Contract §3–6.

### US-03 · Не удалось подтвердить выход — P1

При иной ошибке, сети, timeout или неожиданном `2xx` UI переходит
в `failed` и сохраняет текущий экран/аккаунт **только пока auth-контекст
актуален и ещё локально авторизован**. Доступны «Повторить выход»
и «Закрыть уведомление»; данные не очищаются оптимистически.
UI не утверждает ни активность сессии, ни успешное закрытие.

Ручной повтор создаёт новый ID при свободной auth-операции. Если сервер
успел закрыть сессию, повторный `401` завершает локальный вход по US-02.
Если auth уже очищена сторонним `401`, ошибка прежнего Logout не
возвращает исходный экран и не заменяет уведомление нового поколения.
**Изменение:** LOG-03, LOG-04, LOG-08, LOG-09; ADR-05, ADR-06, ADR-09,
ADR-10; Contract §6–7.

### US-04 · Повторные действия и конкурирующие события — P1

Двойной клик, Enter, закрытие dropdown, повторное открытие меню
и смена hash в `pending` не дублируют запрос и не отменяют ожидание.
Новые защищённые действия и отправка Login/Logout заблокированы.
Попытка не ставится автоматически в очередь.

Актуальный protected-`401` приоритетно очищает auth-контекст, даже
в `pending`. Экран входа появляется, но отправка login остаётся
заблокированной до клиентского завершения Logout или его timeout.
Старые результаты/таймеры не меняют новый вход или новую попытку.
**Изменение:** LOG-03, LOG-04; ADR-05, ADR-06; Contract §6–7.

### US-05 · Возврат и проверка сессии — P1

Back/Forward и защищённый hash после очистки не возвращают личные данные.
При reload обычная `/v1/account/me` даёт: `401` → вход; недоступность →
baseline-экран ошибки загрузки с «Повторить». Уход со страницы,
перезагрузка и закрытие вкладки не подтверждают Logout.

Новый успешный login показывает только новый актуальный аккаунт,
открывает главную и сбрасывает прежние данные/уведомления.
**Уточнение:** ADR-05, ADR-06; LOG-03, LOG-04; Contract §6.1–7.

### US-06 · Другая вкладка — P2

Вкладка с общей закрытой сессией очищает UI при следующем актуальном
protected-`401` или reload. Мгновенный broadcast/polling не требуется.
При конкуренции login одной вкладки с Logout другой допускается потеря
новой cookie от позднего удаляющего ответа. Новая независимая запись
сессии в БД этим Logout не закрывается. Игнорирование callback защищает
UI, а не применение браузером `Set-Cookie`.
**Уточнение:** LOG-03; ADR-05, ADR-06; Contract §7–8.

## 4. Состояния интерфейса

### 4.1. Модель состояния и переходы

Состояние авторизации отделено от занятости auth-операции.
`idle` и `failed` ниже означают `authenticated/idle` и
`authenticated/failed`; состояния `signed-out`/`unauthenticated`
не содержат локально авторизованного аккаунта.

| Состояние | UI и действия | Допустимые переходы |
| --- | --- | --- |
| `idle` | Обычный Header и навигация, кнопка «Выйти» без «Скоро»; нет ошибки Logout | При свободной auth-операции Logout → `pending`; актуальный protected-401 → `unauthenticated` |
| `pending` | Меню закрыто, прогресс «Выходим…» вне dropdown; повтор, новый login и новые защищённые действия заблокированы | Актуальные 204 → `signed-out`; Logout-401 или protected-401 → `unauthenticated`; прочая ошибка/timeout при сохранённой auth → `failed` |
| `failed` | Текущий экран и аккаунт сохранены без обещания активности сессии; ошибка без автоскрытия; «Повторить выход», «Закрыть уведомление»; обычные действия снова доступны | Ручной повтор при свободной операции → `pending` с новым ID; закрытие ошибки → `idle`; актуальный protected-401 → `unauthenticated` |
| `signed-out` | AuthPage на `#/login`, нет Header/защищённых экранов; «Вы вышли из аккаунта.» | При свободной auth-операции успешный baseline-login → новый auth-контекст и главная |
| `unauthenticated` | AuthPage на `#/login`, нет Header/защищённых экранов; «Сессия недействительна. Войдите снова»; повтора Logout нет | Если Logout ещё ожидается, login заблокирован; после освобождения операции успешный baseline-login → новый контекст и главная |

Новый результат Logout применим только к актуальным поколению и ID.
В `unauthenticated` после стороннего `401` завершение прежнего Logout
не меняет экран/уведомление: оно может освободить лишь собственную
auth-операцию. Это не дополнительный переход в `failed` или `signed-out`.
**Изменение машины состояний:** LOG-04; ADR-05, ADR-06; Contract §6.

Состояние Logout принадлежит приложению, а не dropdown. Смена hash
не сбрасывает блокировку. Аккаунт, поиск и пагинация пользователей,
выбранная карточка, личные ошибки и состояния в памяти очищаются
одновременно со скрытием защищённых экранов и Header, без кадра личных
данных на login. На ошибке snapshot не используется для восстановления
авторизации. **Уточнение:** LOG-04; ADR-06; Contract §6.

### 4.2. Поколения авторизации и приоритет событий

1. Каждый защищённый запрос привязан к поколению auth-контекста,
   Logout дополнительно имеет уникальный ID попытки. Очистка или замена
   auth-контекста меняет поколение; новый успешный login создаёт новый
   контекст. Завершённый/просроченный ID не становится актуальным вновь.
2. Перед изменением UI проверяются поколение и актуальность ID.
   Старое событие, включая `401`, ошибку, успех или таймер, не меняет
   данные, hash, уведомления и ожидание новой попытки/поколения.
3. Protected-`401` актуального поколения очищает auth из `idle`,
   `failed` и `pending`. После очистки события прежнего поколения
   не могут вернуть данные или изменить новый итог. Если 204/401 Logout
   обработан первым и сменил поколение, более поздний старый protected-401
   также игнорируется. Искусственный приоритет старого события не вводится.
4. Ошибка/timeout Logout сохраняет экран только при актуальной авторизации.
   Если её уже нет, UI остаётся `unauthenticated`; новый login не сбрасывается.
5. Завершение старого ожидания освобождает только принадлежащую ему
   auth-операцию. Старый callback/таймер не снимает блокировку новой.
6. Ранее запущенные защищённые запросы могут завершиться на сервере;
   после смены поколения их данные не применяются. Клиентская отмена
   допустима, но не доказывает rollback серверных эффектов.

**Новые уточнения V1:** LOG-03, LOG-04; ADR-05, ADR-06, ADR-11;
Contract §6, §8. Поколения защищают состояние приложения и не управляют
cookie браузера.

### 4.3. Сериализация Login/Logout

- В одной вкладке не более одной активной клиентской auth-операции.
  Ограничение действует в обе стороны: login во время Logout и Logout
  во время login не отправляются и не ставятся автоматически в очередь.
- Baseline-проверка аккаунта после успешного запроса login относится
  к той же login-операции: до её завершения auth-занятость сохраняется.
- Сторонний protected-401 может открыть AuthPage, но не освобождает
  Logout-операцию; отправка login остаётся недоступной до её завершения.
- Клиентское завершение включает получение/чтение результата либо
  завершение ожидания по ошибке/timeout. После него доступен явный
  ручной повтор или новый login на доступном экране.
- После timeout серверная операция может продолжаться. Не требуется
  ожидать доказанного окончания транзакции, но нельзя обещать отсутствие
  перекрытия на сервере или абсолютную сохранность новой cookie.
- Глобальный lock вкладок не требуется. Promise-ignore/abort не является
  доказательством невозможности позднего cookie-эффекта.

**Новое требование:** LOG-03, LOG-04; ADR-05, ADR-06, ADR-10;
Contract §7–8. Сохранность React-состояния не подменяет сохранность cookie.

## 5. Ошибки и неопределённый результат

Таблица применяется к актуальной попытке при локально сохранённой auth.
Во всех иных случаях действует приоритет поколений из §4.

| Результат | Точный текст UI | Действие |
| --- | --- | --- |
| Только `204` | «Вы вышли из аккаунта.» | `signed-out`, очистка и вход |
| Logout-`401`, в том числе с отсутствующим/невалидным JSON | «Сессия недействительна. Войдите снова» | `unauthenticated`, очистка и вход, без повтора Logout |
| Нет достоверного HTTP-ответа, сеть / локальный status `0` | «Не удалось подтвердить выход: нет соединения. Попробуйте ещё раз.» | `failed`, ручной повтор |
| UI timeout либо `504` | «Не удалось подтвердить выход: сервер не ответил вовремя. Попробуйте ещё раз.» | `failed`, ручной повтор |
| `502`, `503` | «Не удалось подтвердить выход: сервис временно недоступен. Попробуйте позже.» | `failed`, ручной повтор |
| `400`, `403`, `405`, прочие ошибки, неожиданный `2xx` | «Не удалось подтвердить выход. Попробуйте ещё раз.» | `failed`, ручной повтор; не считать успехом |

`403` от Origin или CSRF — отказ до проверки сессии, не истечение и не
Logout-401. Он не очищает актуальную auth как успех и не использует
текст «Недостаточно прав для поиска пользователей.».
`200/201/202` и другие не-204 успехи не подтверждают выход.
**Изменение:** LOG-01, LOG-02, LOG-06, LOG-08; ADR-02, ADR-03, ADR-07,
ADR-09; Contract §4–6.

Контролируемые ошибки API и proxy имеют `error:string`, `message:string`,
`details:object` и no-store. Клиентская логика основана на достоверном
HTTP-статусе, а не тексте message или полной очередности credential-reason.
При malformed/non-JSON ответе сохраняется безопасный fallback по статусу:
`401` очищает актуальную auth, остальные ошибки не дают ложного успеха.
UI не выводит сырые message/details, секреты или исключения. Нет JWT,
Cookie/Set-Cookie, secret/hash или SQL в прикладных логах/JSON.
**Уточнение:** LOG-08; ADR-09; Contract §4.

### Временные бюджеты и повтор

- Proxy: **15 000 мс**, от запуска upstream до окончания чтения ответа.
  Успешный ответ до окончания этого чтения браузеру не отправляется.
- UI: **20 000 мс** от отправки Logout, включая получение/чтение результата.
  Более ранний результат, например proxy-504, завершает ожидание сразу.
- Если за 20 секунд результата нет, ожидание завершается: при актуальной
  auth → `failed`; при уже очищенной → сохранить `unauthenticated`.
  ID инвалидируется, освобождается только эта локальная auth-операция.
  Позднее завершение/таймер не влияет на новую попытку или login.
- Таймеры не срабатывают раньше своего бюджета без другого результата.
  Разница 15/20 секунд не гарантирует доставку `504` и не задаёт SLA БД.
- Timeout, `502/504`, обрыв/abort не доказывают rollback или закрытие.
  Commit мог состояться. Успех без `204` не показывается; явный повтор
  может получить `401`, это штатный результат идемпотентного эффекта.
- Ни UI, ни proxy не повторяют Logout автоматически, включая
  `details.retryable`. Новый POST возможен только по действию пользователя.

**Изменение 15 → 20 секунд UI:** LOG-09, LOG-03; ADR-05, ADR-10;
Contract §2.2, §7–8.

Уведомления успеха/недействительности живут на AuthPage, закрываются
вручную и сбрасываются при новом входе. Ошибка не исчезает по таймеру;
закрытие ошибки возвращает `failed` в `idle` только при сохранённой auth.
**Уточнение:** LOG-04; ADR-06; Contract §6.1.

## 6. Ожидаемое поведение API и Node.js proxy

Это утверждённый Contract, а не перечень предложений V1.

### 6.1. Запрос, CSRF и приоритет валидации

| Аспект | Обязательное поведение | Основание изменения/уточнения |
| --- | --- | --- |
| Путь/метод | Относительный `POST /v1/auth/logout`, без ID в URL | ADR-01 |
| Форма | Body ровно 0 байт, query отсутствует; не отправлять даже `{}`, `null` или пробел. Content-Type при пустом body допустим | LOG-07; ADR-08 |
| CSRF | UI задаёт единственное значение `X-AnimeMap-Logout: 1`; регистр имени не значим. Это публичная константа, не секрет/аутентификация | LOG-01; ADR-02 |
| Credentials/cache | `credentials: 'same-origin'`, `cache: 'no-store'`; JS не читает JWT и не формирует Authorization | ADR-01, ADR-03 |
| Успех | Только `204`, нулевое тело, без JSON/JWT/срока/Location/redirect | LOG-08; ADR-01, ADR-09 |
| Отказы до cookie | Неподдерживаемый метод → 405; недопустимый присутствующий Origin POST → proxy-403; затем CSRF → 403; затем форма → 400; только после этого credential | LOG-01, LOG-02, LOG-07; ADR-02, ADR-03, ADR-08 |

Отсутствующий, неверный или неоднозначный множественный CSRF-заголовок
даёт `403` независимо от body/query/cookie. После корректного CSRF любое
непустое тело (включая повреждённый JSON) или любой query-параметр
(включая пустое значение) даёт `400` до проверки cookie, без изменения
сессии/cookie. Наличие Content-Type при нулевом body не ошибка.
Bearer без cookie не аутентифицирует запрос; body/query не выбирают сессию.
**Основание:** LOG-01, LOG-07; ADR-02, ADR-08; Contract §2–4.

### 6.2. Публичная граница Node.js proxy

1. Пропускать POST Logout на тот же путь API; передавать Cookie и
   исходный клиентский CSRF-заголовок. Отсутствующее значение не добавлять,
   неверное/множественное не исправлять. Backend независимо проверяет
   CSRF и credential.
2. Присутствующий Origin сравнивать по нормализованным **scheme, hostname,
   effective port** публичного origin. Другие схема/hostname/порт,
   `null` и невалидное значение → `403/access_denied`,
   `details.reason=origin_check_failed`, без upstream-операции.
   Эквивалентный нормализованный порт проходит. Публичная схема определяется
   доверенной конфигурацией/транспортом, не произвольным клиентским
   `X-Forwarded-Proto`; способ инфраструктурной настройки здесь не выбирается.
3. Отсутствие Origin не означает доверия и не отменяет CSRF:
   без обоих → `403`; без Origin с правильным CSRF → обычная проверка.
4. Не удалять body/query перед валидацией. Для распознанного непустого
   body не подменять обязательный `400` прикладным статусом общего буфера
   (например, `413`); приоритет Origin/CSRF сохраняется.
5. Передавать статусы, `Set-Cookie`, `Cache-Control`, `Allow` без потери
   семантики; не добавлять body к `204`. Контролируемые proxy-ошибки
   используют envelope и no-store, как API.
6. Не следовать redirect API. Неожиданный `3xx` Logout → контролируемый
   `502/service_unavailable`, `reason=upstream_failure`, без применения
   его `Set-Cookie`. Регистрационное преобразование `303→201` сюда
   не применяется; baseline регистрации не меняется.
7. GET и прочие неподдерживаемые методы на распознанном пути →
   `405/method_not_allowed`, `Allow: POST`, no-store, envelope там,
   где HTTP разрешает body; HEAD без тела. Они не проверяют сессию,
   не меняют БД/cookie. OPTIONS не аутентифицирует/не меняет сессию
   и не разрешает cross-origin credentialed доступ.
8. Upstream timeout 15 секунд → `504/service_unavailable`,
   `reason=upstream_timeout`, если browser-соединение доступно;
   другая ошибка upstream-связи → `502`, `reason=upstream_failure`.
   Эти ответы не Logout-401 и не изменяют cookie. Автоповторов нет.

**Расширение V1:** LOG-01, LOG-02, LOG-07, LOG-08, LOG-09;
ADR-02, ADR-03, ADR-08, ADR-09, ADR-10; Contract §2, §4, §7.

### 6.3. Cookie и серверные гарантии, значимые для UI

- На фактическом `204` и каждом Logout-`401` удаляется только
  `session_token`: пустое значение, `Path=/`, host-only без Domain,
  `Max-Age=0`, истёкший Expires, `Secure; HttpOnly; SameSite=Lax`.
  Scope совпадает с login. Порядок атрибутов/кавычки пустого значения
  не существенны. Proxy сохраняет backend-команду, не генерирует её сам.
- На `400/403/405/500/502/503/504` и иных ошибках не отправляется
  устанавливающий/удаляющий `Set-Cookie` для session_token. Это обещание
  конкретного ответа, не неизменности cookie при конкурирующих ответах.
- `204` подтверждает commit закрытия только предъявленной сессии.
  Обычное Auth-продление не вызывается; Logout не меняет времена
  использования/истечения. После commit старый JWT не аутентифицирует,
  независимые сессии не затрагиваются. Доставка cookie и commit не атомарны.
- При неактивном владельце остальные выполненные условия позволяют
  `204`; реактивация не восстанавливает закрытую сессию. Истечение,
  включая равенство времени и наступление срока при ожидании, даёт `401`,
  а не новое закрытие. Отсутствующий/удалённый владелец также даёт `401`.
- Повтор после закрытия → `401/session_closed`, после удаления cookie →
  `401/missing_session_cookie`; исходный closed_at не переписывается.
  Logout-401 не доказывает новое закрытие записи.
- Ошибка read/update/flush/commit не даёт `204`/удаления cookie;
  неизвестный commit не означает гарантированный rollback.
  При повреждённом хэше — `400`, не `401`; недоступности БД — `503`.
- Уже аутентифицированная бизнес-операция может завершиться после
  выхода; UI не обещает её отмену или откат. Конкурентное обычное Auth
  не должно восстановить уже закрытую сессию.
- JS не читает/удаляет HttpOnly cookie, не декодирует и не сохраняет JWT
  в localStorage/sessionStorage. Рабочая проверка Secure cookie — через
  HTTPS браузер → Node.js proxy; допущения localhost HTTP из README
  не заменяют эту проверку. Cross-origin схема не добавляется.

**Уточнение V1:** LOG-03, LOG-05, LOG-06, LOG-08;
ADR-01, ADR-03, ADR-04, ADR-05, ADR-07, ADR-09, ADR-11;
Contract §3–5, §8. Серверные гарантии здесь — зависимости UI, а не
перенос реализации транзакций в Frontend.

## 7. Доступность и представление

Сохранены требования V1; уточнения занятости и фокуса соответствуют
ADR-05, ADR-06 и Contract §6.1 (LOG-03, LOG-04).

1. Сохраняются мышь/касание/клавиатура, Escape и возврат фокуса на
   триггер меню. «Выйти» — настоящая кнопка, запускаемая Enter/Space,
   с понятным именем, без «Скоро»; декоративная иконка скрыта от скринридера.
2. Прогресс вне dropdown, `role="status"`, текст «Выходим…» со спиннером;
   занятость и недоступность объявляются, не только окрашиваются.
3. При запуске фокус возвращается на фокусируемый триггер меню,
   который в pending не разрешает действий. Hash/закрытие меню не
   снимают блокировку. Если protected-401 открыл login при занятом
   Logout, недоступность отправки login также объявляется.
4. Ошибка имеет `role="alert"`; повтор/закрытие доступны клавиатурой,
   фокус не теряется. В failed ошибка не исчезает по таймеру.
5. При переходе на login фокус на заголовке; итоговое уведомление
   имеет `role="status"`. Приоритет событий не позволяет старому
   ответу заменить уведомление нового поколения.
6. На узком экране сообщения/действия не обрезаются; спиннер имеет текст.
   Существующее оформление AnimeMap сохраняется без редизайна Header.

| Недостаточная защита поздних ответов | Локальная сериализация плюс поколения/ID; отдельно приняты cookie-race после timeout и между вкладками | LOG-03; ADR-05, ADR-06, ADR-10 |
| Безусловное сохранение экрана на ошибке | Только при актуальной auth; protected-401 очищает, auth-lock живёт до завершения попытки | LOG-04; ADR-06, ADR-05 |
| «Сессия истекла» для любого 401 | Нейтральное точное сообщение; неактивный владелец может получить 204, 401 не доказывает новый close | LOG-06; ADR-07, ADR-11 |
| Неясная обработка лишнего ввода | Любое непустое body/query → 400 после CSRF | LOG-07; ADR-08 |
| Envelope только как общее ожидание | API+proxy envelope/no-store, fallback по статусу, только точный 204 | LOG-08; ADR-09 |
| UI 15 секунд | Proxy 15 секунд, UI 20 секунд, явный повтор, неизвестный серверный результат | LOG-09; ADR-10, ADR-05 |
| Серверное подтверждение | Commit до 204, без Auth-продления; другие сессии неизменны, старые бизнес-операции могут завершиться | ADR-11 |
