# AnimeMap — UI-спецификация Logout V1

**Версия:** 1.0

**Дата:** 2026-11-02

**Автор:** UI Team / Lead Frontend Engineer

**Статус:** самостоятельный проект для совместного согласования.

Документ описывает целевое поведение интерфейса. Он не утверждает новый
HTTP-контракт и не разрешает реализацию. Реализация возможна только после
совместного согласования UI- и Backend-спецификаций.

## 1. Источники и исходное состояние

Изучены только следующие источники:

- `frontend/src/components/Header.tsx`;
- `frontend/src/App.tsx`;
- `frontend/src/api/client.ts`;
- `docs/auth.md`;
- `docs/endpoints/auth.md`;
- `agent-rules/AGENTS.md`, `agent-rules/codestyle.md`,
  `agent-rules/naming.md`.

Спецификация Backend Team не читалась и не использовалась.

### Подтверждённые факты

1. В меню аккаунта Header есть кнопка «Выйти» с пометкой «Скоро».
   Она закрывает меню и показывает уведомление
   «Выход появится позже. Ваша сессия остаётся активной.».
2. App хранит текущий аккаунт в памяти, при запуске вызывает
   `GET /v1/account/me` и показывает AuthPage, если аккаунта нет.
   Неавторизованный пользователь перенаправляется на `#/login`.
3. Страницы аккаунта и Admin Panel имеют обработчик истечения сессии:
   очистка аккаунта и переход на `#/login`.
4. API-клиент использует `/v1`, `credentials: 'same-origin'`,
   `cache: 'no-store'`. Метода Logout пока нет. Клиент обрабатывает
   отсутствие JSON-тела и представляет ошибки через `ApiError`;
   сетевой сбой имеет статус `0`.
5. Единственный JWT хранится в серверной `session_token` cookie
   с `HttpOnly; Secure; SameSite=Lax; Path=/`. JavaScript не читает
   токен и не формирует `Authorization`.
6. По `docs/auth.md` выход закрывает текущую серверную сессию
   установкой `closed_at` и удаляет cookie серверным `Set-Cookie`.
   Только локальная очистка аккаунта не является серверным выходом.
7. Повторное закрытие модели идемпотентно, но повторный HTTP-запрос
   с недействительной сессией проходит обычный отказ аутентификации.
   Закрытая сессия не должна возобновляться параллельным запросом.
8. `docs/endpoints/auth.md` определяет только login/register.
   Метод, путь, тело и успешный статус Logout пока не закреплены.
9. По правилам проекта браузер работает через frontend-прокси,
   пропускающий разрешённые `/v1/` ручки. Доступность нового маршрута
   через прокси — интеграционная зависимость будущей реализации.

Все требования ниже — предложение UI-команды V1. Ожидания нового API
отдельно перечислены в разделе 6 и требуют совместного согласования.

## 2. Цель и границы

**Цель:** пользователь любой роли может через существующую кнопку
завершить текущую сессию и попасть на экран входа с понятным результатом.

В объём входят выход с главной, аккаунта и Admin Panel, ожидание ответа,
ошибки, ручной повтор, истёкшая сессия, защита от повторных действий,
очистка пользовательского UI и доступность с клавиатуры.

Выход относится только к текущей сессии. Он не закрывает другие
независимые сессии на устройствах пользователя и не меняет аккаунт,
пароль или роль. Вкладки с общей cookie используют одну сессию.

В V1 не входят «Выйти на всех устройствах», refresh-токены, управление
сессиями, автоматический повтор Logout и офлайн-выход с заявлением
об успешном завершении серверной сессии. Отдельное подтверждение
нажатия не требуется: действие обратимо повторным входом.

## 3. Пользовательские сценарии

### US-01 · Обычный выход — P1

**Как** вошедший пользователь любой роли, **я хочу** нажать «Выйти»,
**чтобы** завершить текущую сессию и освободить интерфейс для нового входа.

1. Пользователь открывает существующее меню аккаунта и выбирает «Выйти».
2. Меню закрывается; интерфейс немедленно показывает «Выходим…».
3. Выполняется один Logout-запрос с cookie браузера.
4. После подтверждённого успеха очищаются аккаунт и данные защищённых
   экранов, отображается `#/login` с уведомлением «Вы вышли из аккаунта.».
5. Пользователь может снова войти; успешный вход открывает главную
   согласно существующему поведению App.

Сценарий одинаков для `user`, `moderator`, `admin`, независимо
от доступности Admin Panel.

### US-02 · Сессия уже недействительна — P1

Если Logout возвращает `401` из-за отсутствующей, истёкшей, закрытой
или иной недействительной сессии, UI очищает локальную авторизацию
и открывает `#/login`. Сообщение: «Сессия истекла. Войдите снова.».
Это результат «уже не авторизован», а не подтверждение выполненного
этим запросом закрытия сессии. Повтор Logout не предлагается.

### US-03 · Не удалось подтвердить выход — P1

При сетевой ошибке, таймауте или ошибке сервера пользователь остаётся
на исходном экране. UI показывает ошибку и доступное действие
«Повторить выход». Данные аккаунта не очищаются оптимистически;
интерфейс не утверждает, что сессия активна или успешно закрыта.
Ручной повтор запускает новую попытку; её `401` обрабатывается по US-02.

### US-04 · Повторное нажатие и запоздавшие ответы — P1

Быстрый двойной клик, повтор Enter или повторное открытие меню
не создают второй Logout-запрос, пока выполняется первый.
Ответы ранее начатых запросов аккаунта/поиска не должны восстановить
данные или старую авторизацию после выхода и после нового входа.

### US-05 · Возврат и проверка сессии — P1

После успешного выхода Back/Forward, переход на `#/account` или
`#/admin` не восстанавливают защищённый UI. После перезагрузки App
проверяет сессию через `/v1/account/me`; ожидаемый `401` ведёт на вход.
При недоступности этой проверки применяется существующий экран
ошибки загрузки с «Повторить», а не ложная авторизация.

### US-06 · Другая вкладка — P2

Закрытие общей сессии действует и на другие вкладки. При следующем
защищённом запросе, получившем `401`, или при перезагрузке такая
вкладка очищает локальные данные и показывает вход. Мгновенная
межвкладочная синхронизация и фоновый polling в V1 не требуются.

## 4. Состояния интерфейса

| Состояние | Представление и доступные действия | Переход |
| --- | --- | --- |
| `authenticated/idle` | Обычный Header, «Выйти» без «Скоро»; существующая навигация | Нажатие → `pending` |
| `pending` | Меню закрыто; видимое «Выходим…» со спиннером, доступное вне dropdown; повторный выход и защищённые действия заблокированы | Успех → `signed-out`; `401` → `unauthenticated`; ошибка → `failed` |
| `failed` | Исходный экран и аккаунт сохранены; сообщение об ошибке, «Повторить выход», «Закрыть уведомление»; обычные действия снова доступны | Повтор → `pending`; закрытие → `idle`; последующий `401` → `unauthenticated` |
| `signed-out` | AuthPage на `#/login`, Header и защищённые экраны отсутствуют; «Вы вышли из аккаунта.» | Новый вход → существующий сценарий входа |
| `unauthenticated` | AuthPage на `#/login`; сообщение о недействительной сессии; Header отсутствует | Новый вход → существующий сценарий входа |

- Состояние Logout принадлежит уровню приложения и переживает закрытие
  dropdown; исчезновение меню не скрывает прогресс или ошибку.
- В `pending` не запускаются новые защищённые операции. Смена hash
  не отменяет Logout и не сбрасывает блокировку. Перезагрузка или
  закрытие вкладки не считаются подтверждением выхода; при новом
  открытии источником истины служит проверка серверной сессии.
- Аккаунт очищается вместе со скрытием защищённых экранов, чтобы
  не возникало промежуточного кадра с личными данными на экране входа.
- После выхода сбрасываются данные аккаунта, поиска пользователей,
  выбранной карточки и пользовательские ошибки/состояния в памяти UI.
  Результаты старых запросов игнорируются либо запросы отменяются;
  отмена клиентского запроса не доказывает отмену серверной операции.
- Уведомление об успехе или истечении размещается на экране входа,
  а не в размонтированном Header; оно закрывается вручную и сбрасывается
  при новом входе. Ошибка выхода не исчезает по таймеру.

## 5. Ошибки и неопределённый результат

| Результат | Сообщение UI | Действие |
| --- | --- | --- |
| `401` | «Сессия истекла. Войдите снова.» | Очистить UI, открыть вход; без повтора Logout |
| Сетевая ошибка / статус клиента `0` | «Не удалось подтвердить выход: нет соединения. Попробуйте ещё раз.» | Остаться на экране, предложить ручной повтор |
| Таймаут клиента или `504` | «Не удалось подтвердить выход: сервер не ответил вовремя. Попробуйте ещё раз.» | То же; не считать сессию активной или закрытой |
| `502`, `503` | «Не удалось подтвердить выход: сервис временно недоступен. Попробуйте позже.» | То же |
| `400`, `403`, прочие `4xx`, `5xx`, неожиданный ответ | «Не удалось подтвердить выход. Попробуйте ещё раз.» | То же; не подменять ошибку успехом |

Предложение UI V1: ожидание одной попытки ограничить **15 секундами**,
после чего перейти в `failed` и игнорировать её запоздавшее завершение.
Автоматических повторов нет. Отмена ожидания не гарантирует, что сервер
не успел закрыть сессию; повтор может законно вернуть `401`.

`403` нельзя показывать существующим текстом клиента «Недостаточно прав
для поиска пользователей.»: это чужой сценарий. UI использует сообщения
Logout, не выводит сырые исключения или `details`, токены и секреты.
Точное успешное представление ответа определяется при согласовании;
неожиданный статус не должен превращаться в успех только из-за `2xx`.

## 6. Ожидаемое поведение API — предложение для согласования

Следующие пункты **не являются существующим контрактом**.
Они фиксируют ожидания UI-команды к будущему Logout.

| Аспект | Предложение UI V1 |
| --- | --- |
| Метод и URL | `POST /v1/auth/logout` |
| Вход | Без тела, query-параметров, ID аккаунта или сессии; текущая сессия определяется cookie |
| Передача cookie | Same-origin запрос с `credentials: 'same-origin'`, через существующий frontend-прокси |
| Успех | `204 No Content`, без JSON и HTTP-редиректа; UI сам переходит на `#/login` |
| Серверная гарантия успеха | Текущая сессия закрыта и изменение сохранено до успешного ответа |
| Cookie при успехе | Сервер удаляет `session_token` через `Set-Cookie` с теми же именем, `Path=/` и областью действия; например, `Max-Age=0`; сохраняет атрибуты безопасности |
| Кэширование | `Cache-Control: no-store`; ответ не кэшируется; клиент сохраняет `cache: 'no-store'` |
| Нет действительной сессии | `401`, включая повтор после уже успешного закрытия; UI считает пользователя неавторизованным |
| Ошибки | Существующий формат `error/message/details`; инфраструктурная недоступность — `503`, не `401` |
| Права | Выход из собственной текущей сессии доступен всем аутентифицированным ролям |
| Параллельные запросы | После закрытия сессия не продлевается и не восстанавливается; уже аутентифицированная операция может завершиться согласно `docs/auth.md` |

Дополнительные ожидания интеграции:

- Прокси должен пропускать согласованный маршрут и передавать статус,
  `Set-Cookie` и `Cache-Control` без потери. Конфигурация не меняется
  на этапе этой спецификации.
- UI не удаляет HttpOnly cookie, не декодирует JWT, не хранит токены
  в localStorage/sessionStorage и не отправляет bearer-заголовок.
- UI не требует токен, время истечения или данные аккаунта в ответе.
- После подтверждённого успеха дополнительный `/account/me` не нужен
  для показа входа. После перезагрузки используется обычная проверка.
- `401` не доказывает выполнение закрытия или удаление cookie.
  Должен ли сервер удалять недействительную cookie при `401`, необходимо
  согласовать; UI не зависит от возможности прочитать `Set-Cookie`.

## 7. Доступность и представление

1. Сохраняются существующие способы открытия меню мышью, касанием
   и клавиатурой, закрытие Escape и возврат фокуса на триггер.
2. «Выйти» остаётся настоящей кнопкой с понятным доступным именем;
   запуск возможен Enter/Space. Декоративная иконка скрыта от скринридера.
3. «Выходим…» объявляется через `role="status"`; область операции
   обозначается занятой. Блокировка повторного действия доступна
   вспомогательным технологиям, не выражается только цветом.
4. После закрытия dropdown при запуске фокус возвращается на доступный
   триггер меню. В `pending` меню не открывается для действий; триггер
   может оставаться фокусируемым с объявленным недоступным состоянием.
5. Ошибка объявляется через `role="alert"`, остаётся читаемой вне меню;
   кнопки повтора и закрытия доступны с клавиатуры. Фокус не теряется.
6. После перехода на вход фокус перемещается на заголовок экрана входа;
   итоговое уведомление доступно скринридеру через `role="status"`.
7. Прогресс и сообщения читаемы на узком экране, не обрезают действия;
   спиннер сопровождается текстом. Существующее оформление AnimeMap
   сохраняется без отдельного редизайна Header.

## 8. Проверяемые критерии приёмки

Критерии предназначены для будущей реализации после согласования.
Проверки UI с подменой ответов не заменяют проверку серверного закрытия.

| ID | Given / When / Then |
| --- | --- |
| AC-01 | **Дано:** пользователь `user`, `moderator` или `admin` на доступной ему странице. **Когда:** открыт Header. **Тогда:** «Выйти» доступна, пометки «Скоро» и прежнего уведомления-заглушки нет. |
| AC-02 | **Дано:** валидная сессия. **Когда:** выбран выход. **Тогда:** отправлен ровно один запрос по согласованному контракту с cookie, меню закрыто, «Выходим…» видимо до завершения, защищённые действия заблокированы. |
| AC-03 | **Дано:** Logout ожидает ответа. **Когда:** двойной клик, повтор Enter или смена hash. **Тогда:** второй запрос не отправлен, состояние ожидания сохраняется. |
| AC-04 | **Дано:** согласованный успешный ответ. **Когда:** UI его обработал. **Тогда:** аккаунт и защищённые данные очищены, Header отсутствует, открыт `#/login`, показано «Вы вышли из аккаунта.». |
| AC-05 | **Дано:** отсутствующая, истёкшая или ранее закрытая сессия. **Когда:** Logout отвечает `401`. **Тогда:** открыт вход, показано сообщение об истечении, нет ошибки с предложением повторить Logout и нет утверждения об успешном закрытии этим запросом. |
| AC-06 | **Дано:** сеть недоступна либо получен `502`/`503`/`504`/`500`. **Когда:** попытка завершена. **Тогда:** аккаунт и исходный экран сохранены, блокировка снята, видна соответствующая ошибка и «Повторить выход», нет сообщения об успехе. |
| AC-07 | **Дано:** сервер не отвечает. **Когда:** прошло 15 секунд. **Тогда:** показана ошибка таймаута, доступен ручной повтор; поздний ответ прежней попытки не меняет состояние новой попытки или нового входа. |
| AC-08 | **Дано:** предыдущий ответ потерян после закрытия сессии сервером. **Когда:** ручной повтор возвращает `401`. **Тогда:** UI корректно переходит на вход без бесконечного повтора. |
| AC-09 | **Дано:** Logout вернул `403` или неожиданный ответ. **Тогда:** показана ошибка Logout, отсутствует текст про поиск пользователей, защищённый UI не сброшен как при успехе. |
| AC-10 | **Дано:** выход завершён, старые запросы аккаунта/поиска ещё выполнялись. **Когда:** приходят их ответы. **Тогда:** личные данные, Header и прежняя авторизация не восстанавливаются, включая случай нового входа другим пользователем. |
| AC-11 | **Дано:** подтверждённый выход. **Когда:** Back/Forward, прямой переход на защищённый hash или перезагрузка с `401` от `/account/me`. **Тогда:** защищённый UI не отображается, доступен экран входа. |
| AC-12 | **Дано:** экран входа после выхода. **Когда:** пользователь снова успешно входит. **Тогда:** виден новый актуальный аккаунт, главная открыта по существующим правилам, старые данные и уведомление выхода отсутствуют. |
| AC-13 | **Дано:** управление только клавиатурой или скринридером. **Когда:** пользователь выходит либо получает ошибку. **Тогда:** доступны запуск, прогресс, итог, повтор и закрытие уведомления; фокус следует разделу 7. |
| AC-14 | **Дано:** две вкладки с общей сессией. **Когда:** одна завершила выход, другая получила `401` защищённого запроса или перезагружена. **Тогда:** вторая показывает вход и очищает локальные данные. |
| AC-15 | **Дано:** интеграция через frontend-прокси. **Когда:** Logout успешно завершён. **Тогда:** cookie удалена серверным заголовком, прежний JWT больше не аутентифицирует защищённый запрос; независимая другая сессия продолжает работать. |
| AC-16 | **Дано:** просмотр браузерного хранилища и запросов. **Тогда:** UI не хранит и не читает JWT, не отправляет `Authorization`, не пытается удалить HttpOnly cookie через JavaScript. |

## 9. Вопросы совместного согласования и готовность

До реализации необходимо согласовать с Backend Team:

1. Метод и путь Logout, отсутствие тела, успешный статус `204` и отсутствие
   редиректа; если выбран другой ответ, явно обновить UI-спецификацию.
2. Семантику `401` при повторе и отсутствующей cookie, удаление cookie
   на таком ответе и сохранение существующего формата ошибок.
3. Подтверждение сохранённого закрытия перед успехом, удаление cookie
   с правильной областью действия, гарантии конкурентного закрытия.
4. Прохождение нового маршрута и заголовков через frontend-прокси.
5. Предложенный предел ожидания 15 секунд и сценарий потерянного ответа
   с ручным повтором; отличать таймаут UI от отмены серверной операции.

Совместное согласование должно зафиксировать разрешение разногласий
двух спецификаций и итоговый контракт. До этого данный документ остаётся
UI-предложением V1; существующие контракты и исходный код не меняются.
