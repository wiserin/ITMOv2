# AnimeMap — Backend Logout Specification V2

- **Версия:** 2.0, 2026-11-02.
- **Статус:** backend-спецификация по утверждённым ADR-01–ADR-11.
- **Нормативное основание:** [CONTRACT.md](CONTRACT.md), версия 1.0.
- **Cross-review:** [REVIEW.md §6–10](REVIEW.md).
- **История:** [BACKEND_SPEC_V1.md](BACKEND_SPEC_V1.md) сохраняется без изменений.
- **Этап:** сверка спецификаций V2; разрешения реализации нет.

«Должен» и «запрещено» обозначают требования будущей реализации,
а не наличие готового кода или пройденных проверок. При расхождении
исторической V1 с утверждённым контрактом применяется CONTRACT.md.
Новые противоречия передаются архитектору и пользователю, без
самостоятельного изменения решений. Противоречий внутри утверждённого
контракта при подготовке V2 не выявлено. UI_SPEC_V2.md не использовалась.

## 1. Цель, scope и baseline

Logout закрывает только **предъявленную сессию**: запись, выбранную
по `jti` JWT из `session_token` конкретного запроса, после проверки
подписи, payload и индивидуального секрета. Подтверждённый commit
закрытия запрещает последующую аутентификацию копией этого JWT.
Другие независимые сессии не изменяются.

Сохраняются ограничения V1: нет logout всех устройств, выбора другой
сессии по клиентскому ID, refresh/ротации JWT, blacklist, новых хранилищ,
изменения пароля, фоновой очистки или отмены уже прошедших Auth операций.
PostgreSQL — источник истины; Redis для Logout не требуется.

Изученный baseline:

- `docs/auth.md`, `docs/endpoints/auth.md`, `docs/errors.md`;
- `docs/entities/session.md`, `docs/entities/user.md`;
- `docs/repositories.md`, `docs/security.md`;
- `agent-rules/AGENTS.md`, `agent-rules/naming.md`, `agent-rules/codestyle.md`;
- текущие SessionEntity, AuthUseCase, SessionRepository и auth-роутер.

Один JWT содержит только `jti` (UUIDv4), `secret` (непустая строка)
и `iat` (целочисленный NumericDate), подписан EdDSA/Ed25519.
Фиксированный `exp` не вводится. В сущности и БД хранится только
`secret_hash`; срок и закрытие проверяются по серверной записи.
Существующий формат JWT и контракты login/register не меняются.

### 1.1. Узкое исключение для неактивного владельца

**Пригодность для Logout:** запись и владелец существуют,
`closed_at IS NULL`, `now < expires_at`, JWT и secret подтверждены.
`is_active` владельца не ограничивает Logout. Правило одинаково
для `user`, `moderator`, `admin`, административное разрешение не нужно.

Это утверждённое ADR-07 исключение из обобщённых baseline-правил
`docs/auth.md`, `docs/entities/user.md` и правил активности проекта,
а не новое несогласованное решение. Обычный Auth, `/v1/account/me`
и другие защищённые ресурсы продолжают требовать активного владельца.
Logout не активирует аккаунт и не предоставляет дальнейший доступ.

В текущем коде команды close и HTTP Logout ещё нет. Существующих
`SessionRepository.get_by_id(for_update=True)` и `update()` достаточно
для проектируемого сценария; `delete()` не является Logout.
Изменение схемы БД для этой операции не требуется.

## 2. Публичный HTTP-контракт и приоритет проверок

### 2.1. Единственный допустимый запрос

```http
POST /v1/auth/logout HTTP/1.1
Cookie: session_token=<jwt>
X-AnimeMap-Logout: 1
```

Имя маршрута — `auth_logout`, группа OpenAPI — `auth`.
Нет path-параметров, body-полей, query-параметров или ID пользователя.
Токен принимается исключительно из cookie; корректный Bearer без
cookie не аутентифицирует. Cookie определяет сессию именно этого запроса.

Тело должно содержать **ноль байт**. `{}`, `null`, пробел, валидный
и повреждённый JSON — непустой вход и дают `400`. Любой query-параметр,
включая `?session_id=` с пустым значением, даёт `400`.
При нулевом теле `Content-Type` допустим, но не обязателен;
JSON-парсинг не является условием успеха. Нельзя очищать body/query
в proxy или игнорировать их, превращая недопустимый запрос в допустимый.

Имя `X-AnimeMap-Logout` регистронезависимо. Значение должно быть `1`;
отсутствующее, иное или неоднозначное множественное значение — `403`.
Заголовок — публичная CSRF-константа, не аутентификация и не секрет.

### 2.2. Порядок наблюдаемых отказов

1. Неподдерживаемый метод на распознанном пути: `405`, без проверки
   credential/CSRF, изменения сессии или удаления cookie.
2. Для POST присутствующий недопустимый Origin может быть отклонён
   Node.js proxy с `403` до обращения к FastAPI (§3).
3. FastAPI Presentation независимо проверяет CSRF-заголовок:
   отказ — `403`, независимо от body/query/cookie, без чтения сессии
   для аутентификации.
4. После успешного CSRF проверяется нулевое тело и отсутствие query:
   отказ — `400`, независимо от cookie, без аутентификации/изменения БД.
5. Только затем извлекаются и проверяются cookie, JWT, secret и сессия.

Примеры: нет CSRF + непустое тело → `403`; верный CSRF + непустое
тело + нет cookie → `400`; верный CSRF + пустой вход + нет cookie → `401`.
Автоматический JSON-parser/валидация FastAPI не должны менять этот порядок
и возвращать `422` или ошибку тела раньше CSRF.

GET и остальные неподдерживаемые методы возвращают `405` с
`Allow: POST`, `Cache-Control: no-store` и envelope §4 на публичной
и прямой backend-границе. HEAD не содержит тела по правилам HTTP.
OPTIONS не аутентифицирует, не изменяет сессии и не открывает
cross-origin credentialed доступ; новых разрешённых методов не вводится.

## 3. Same-origin proxy и границы ответственности

Единственная топология: **Browser → same-origin Node.js proxy → FastAPI**.
Рабочая проверка Secure cookie — HTTPS. Альтернативного same-site/
cross-origin deployment и CORS-схемы V1 не вводит.
Браузер использует относительный `/v1/auth/logout`,
`credentials: 'same-origin'`, `cache: 'no-store'`.

Ответственность Node.js proxy, согласованная общим контрактом:

- Пропускать POST на тот же путь; обеспечивать публичный `405`.
- Для POST проверять присутствующий Origin по полной нормализованной
  тройке **scheme, hostname, effective port** публичного origin.
  Эквивалентные порты после нормализации совпадают; другая схема,
  hostname, порт, `null` или некорректный Origin → `403`,
  `details.reason=origin_check_failed`, без upstream-операции.
- Публичная схема определяется доверенной конфигурацией/транспортом,
  не произвольным клиентским `X-Forwarded-Proto`.
- Отсутствие Origin само по себе не ошибка и не доверие:
  без CSRF — `403`, с верным CSRF — обычная проверка входа/credential.
- Передавать исходные Cookie и CSRF-заголовок, не синтезировать
  отсутствующее значение и не исправлять неверное/неоднозначное.
  Не удалять тело/query перед валидацией. Общий body-buffer не должен
  подменять согласованный прикладной `400` для распознанного непустого тела.
- Передавать статус, Set-Cookie, Cache-Control и Allow без потери
  семантики; не добавлять JSON к `204`, не генерировать cookie самому.
- Не следовать redirect: неожиданный `3xx` → контролируемый `502`
  без применения его Set-Cookie. Регистрационный `303→201` здесь запрещён.
- Контролируемые ошибки Origin/метода/upstream/timeout соответствуют §4.

FastAPI самостоятельно проверяет CSRF, форму входа и сессию,
независимо от proxy. Proxy не подменяет backend-отказ успехом.
Origin-проверка относится к proxy; она не заменяет CSRF в FastAPI.

## 4. Ответы, ошибки и cookie

### 4.1. Единственный успешный статус

```http
HTTP/1.1 204 No Content
Cache-Control: no-store
Set-Cookie: session_token=; Path=/; Max-Age=0; Expires=Thu, 01 Jan 1970 00:00:00 GMT; Secure; HttpOnly; SameSite=Lax
```

Только `204` подтверждает новое сохранённое закрытие этим запросом.
Тело содержит ноль байт: нет `{}`, `null`, JWT, сроков или UserDTO.
Нет Location/redirect. Ответ не отправляется до подтверждённого commit.
Неожиданные `200/201/202` не являются альтернативными успехами.

### 4.2. Формат контролируемых ошибок

Все контролируемые ответы Logout и proxy-маршрута имеют
`Cache-Control: no-store`. Ошибки с допустимым по HTTP телом — JSON,
`Content-Type: application/json` (charset допустим):

```json
{
  "error": "authentication_failed",
  "message": "Authentication failed",
  "details": {"reason": "session_closed"}
}
```

`error` и `message` — строки, `details` — объект, включая пустой.
Текст message не является машинным контрактом.
Собственные ошибки — существующие общие доменные исключения;
HTTP-маппинг находится в общем Presentation mapper, а не в UseCase/DI.
Routing-ошибка `405` также должна соответствовать этому envelope.

В таблице применены проверки более высокого приоритета из §2.
«Сохранить» означает не отправлять устанавливающий/удаляющий Set-Cookie
для `session_token` этим ответом, а не обещание отсутствия других
параллельных браузерных cookie-эффектов.

| Условие | HTTP / error | details.reason / контекст | Cookie |
| --- | --- | --- | --- |
| Метод не поддерживается | 405 / method_not_allowed | Безопасный объект | Сохранить |
| Недопустимый присутствующий Origin (proxy) | 403 / access_denied | origin_check_failed | Сохранить |
| Нет/неверен/неоднозначен CSRF | 403 / access_denied | csrf_check_failed | Сохранить |
| Непустое тело или любой query | 400 / bad_request | Безопасный контекст валидации | Сохранить |
| Cookie отсутствует/пуста, в том числе только Bearer | 401 / authentication_failed | missing_session_cookie | Удалить |
| Неверные подпись/алгоритм/claims JWT | 401 / authentication_failed | invalid_token | Удалить |
| Отсутствует сессия/владелец | 401 / authentication_failed | session_not_found | Удалить |
| Сессия закрыта | 401 / authentication_failed | session_closed | Удалить |
| Сессия истекла | 401 / authentication_failed | session_expired | Удалить |
| Secret не соответствует хэшу | 401 / authentication_failed | invalid_secret | Удалить |
| Повреждён сохранённый Argon2-хэш | 400 / bad_request | По baseline mapper, без хэша | Сохранить |
| PostgreSQL недоступен, включая commit | 503 / service_unavailable | По baseline mapper | Сохранить |
| Прочая backend-ошибка | По docs/errors.md; неожиданная — 500 / internal_error | Безопасный контекст baseline | Сохранить |
| Upstream timeout (proxy) | 504 / service_unavailable | upstream_timeout | Сохранить |
| Ошибка upstream-связи/неожиданный redirect (proxy) | 502 / service_unavailable | upstream_failure | Сохранить |

Отдельной ошибки `inactive_user` у Logout нет. При единственном дефекте
credential применяется причина из таблицы; полный приоритет нескольких
внутренних дефектов credential не гарантируется.
Deadlock/serialization failure сохраняют baseline-маппинг,
`details.retryable`/`sqlstate`, где применимо; это не разрешение автоповтора.

### 4.3. Защита и удаление cookie

На `204` и **каждом Logout-401**, включая отсутствие cookie,
удаляется только `session_token`: пустое значение, `Path=/`,
host-only scope **без Domain**, `Max-Age=0`, Expires в прошлом,
`Secure`, `HttpOnly`, `SameSite=Lax`. Scope совпадает с login-cookie
на публичном хосте. Порядок атрибутов и кавычки пустого значения незначимы.

На `400/403/405/500/502/503/504` и прочих ошибках Set-Cookie изменения
`session_token` отсутствует. Инфраструктурный/proxy-отказ нельзя
превращать в Logout-401. Logout-401 означает отказ именно проверки
credential/состояния этого сценария, а не любого внешнего слоя.

No-store и cookie-политика применяются к **фактическому** ответу mapper,
включая исключение после подготовки handler-response и ошибку commit.
Если commit не подтверждён, подготовленный `204` и удаление cookie
не должны попасть в HTTP-ответ ошибки.

JWT не читается JavaScript, не хранится в localStorage/sessionStorage,
не отправляется в Authorization. JS не удаляет HttpOnly cookie вручную.
SameSite=Lax — дополнительный барьер, не замена CSRF-заголовку.
JWT, Cookie/Set-Cookie, secret/hash, сырые SQL/параметры и исключения
не включаются в error JSON или прикладное логирование.
Открытый секрет не передаётся в сущность, репозиторий или БД.

## 5. LogoutUseCase, проверки и доменная операция

### 5.1. Отдельный прикладной сценарий

`LogoutUseCase(BaseUseCase)` имеет именованный метод `logout`,
принимающий строку токена, не Request/Response. Зависимости
`UserRepository`, `SessionRepository`, `JwtProviderPort`,
`SecretManagerPort` передаются через конструктор, не создаются внутри.
UseCase не обращается к глобальному config и не является callable.

`get_logout_usecase` собирает экземпляр;
`LogoutUseCaseDI = Annotated[LogoutUseCase, Depends(get_logout_usecase)]`
используется Presentation. DI сборки не выполняет logout.
CSRF, форма HTTP-запроса, cookie и статусы остаются в Presentation.
Пустому запросу и `204` не нужны искусственные JSON Request/Response.

Запрещены `AuthUseCase.authenticate()`, `AuthUseCaseDI`,
`SessionEntity.use()` перед Logout или внутри него: они продлевают
сессию и отдельно коммитят Auth. Logout не возвращает UserDTO
для дальнейшего доступа. Пригодность проверяется самим сценарием,
без отказа по активности и без административного порога для ролей.

### 5.2. Порядок серверных действий

1. Presentation завершает проверки §2 и извлекает cookie.
2. Через существующий JwtProviderPort проверить фиксированный EdDSA,
   подпись, точную структуру и типы `jti`, `secret`, `iat`, UUIDv4.
   Новый exp, иной формат JWT, ротация и доверие ролям из JWT запрещены.
3. Прочитать сессию по `jti`; предварительно проверить существование,
   `closed_at` и `now < expires_at`. Не писать в БД при отказе.
4. Через SecretManagerPort проверить secret по `secret_hash`.
   Синхронный JWT decode выполняется через `asyncio.to_thread`;
   Argon2id verify — существующим async-адаптером вне event loop.
   Дорогой verify выполняется **до row locks**; PostgreSQL I/O — async.
5. **После Argon2id verify** прежний снимок не считается разрешением
   записи: за время verify сессия могла истечь/закрыться, владелец —
   удалиться/стать неактивным. Обязательны последующее актуальное
   перечитывание и повторная проверка под блокировками, а не сохранение
   сущности, прочитанной перед verify.
6. В общей PostgreSQL-транзакции сначала получить пользователя
   через UserRepository с `for_update=True`, затем перечитать сессию
   через `get_by_id(..., for_update=True)`. Порядок строго:
   **пользователь → сессия**, как у Auth/login.
7. **После получения блокировок** повторно проверить существование
   обеих строк, принадлежность сессии заблокированному владельцу,
   неизменность `secret_hash`, по которому выполнен verify,
   `closed_at` и `expires_at` по свежему timezone-aware UTC-времени.
   Это обязательная финальная проверка после долгого verify и ожидания
   locks; отдельная ранняя проверка её не заменяет. При
   `now >= expires_at` — `401`, без закрытия/продления.
   Не использовать старый ORM snapshot. При несоответствии владельца
   или проверенного хэша нельзя закрывать запись на основании старого
   verify: применяются инварианты и общие ошибки baseline, без успеха.
8. `is_active=false` **не** является отказом: если остальные условия
   выполнены, продолжить. Удаление владельца — `401/session_not_found`.
9. На актуальной сущности вызвать доменное закрытие, сохранить
   возвращённую сущность через `SessionRepository.update()` и flush.
10. Дождаться завершения commit фабрикой. Только после подтверждения
    отправить `204` и удаление cookie. На исключении — §6.

Проверка после verify реализуется на актуальном состоянии после locks;
это не разрешение доверять старому сроку и не требование дополнительного
неблокирующего чтения с отдельной гонкой. Во всех исходах Logout
не меняет `last_used_at` и `expires_at`.

### 5.3. Доменное закрытие SessionEntity

Команда `SessionEntity.close(now=...)` сохраняет immutable-модель
`frozen=True, slots=True, kw_only=True` и возвращает сущность:

- если `closed_at` уже задан — эквивалентное состояние с исходным
  временем закрытия; идемпотентность без повторной записи времени;
- иначе `closed_at = max(now, last_used_at)`; время timezone-aware UTC,
  при отсутствии явно переданного now — актуальное UTC-время;
- `closed_at >= last_used_at` даже при обратном сдвиге часов;
- `id`, `user_id`, `secret_hash`, `created_at`, `last_used_at`,
  `expires_at` не меняются; история сохраняется, запись не удаляется.

Расчёт closed_at принадлежит Domain, не ручке, UseCase или ORM.
Команда не знает HTTP, cookie, CSRF и активности владельца.
Как и в V1, доменная возможность закрыть уже истёкшую запись сама
по себе не даёт HTTP-сценарию права считать её пригодной: endpoint
проверяет срок до команды и не материализует истечение.

## 6. Транзакция, commit, истечение и конкуренция

### 6.1. Гарантия сохранения

Репозитории Logout используют одну кэшированную PostgreSQL-сессию.
Commit/rollback принадлежат существующей фабрике сессий;
`PostgresSessionDI` с `scope="function"` завершает транзакцию до отправки
HTTP. Репозитории делают flush, не commit/rollback; отдельный auth commit
или самостоятельный commit в LogoutUseCase не вводится.

Финальная проверка, close и сохранение — одна атомарная операция;
row locks удерживаются до commit/rollback. Flush не доказывает commit,
а успешное завершение UseCase до выхода DI не доказывает успешный HTTP.
**Момент подтверждения отзыва — успешный commit**, до `204` и Set-Cookie.

При сбое read/update/flush/commit успешный ответ не отправляется,
cookie не удаляется. Незавершённая транзакция откатывается владельцем.
Известный rollback означает отсутствие сохранённого close этим Logout.
Если соединение оборвалось при commit и результат неизвестен,
нельзя обещать ни закрытие, ни rollback: возвращается ошибка по mapper,
не `204`, без изменения cookie. Проблема доступности БД — `503`.

Слова «без изменения БД» относятся только к записи этим Logout,
а не запрещают конкурентное продление или каскадное удаление владельца.
Запрещено сохранять старую сущность, обнуляющую closed_at или
перезаписывающую более свежие времена Auth.

### 6.2. Истечение, повтор и граница Logout-401

При `now == expires_at` и `now > expires_at` сессия истекла,
даже при `closed_at IS NULL`: `401/session_expired`, удаление cookie,
без close, продления или материализации closed_at.
Истечение во время verify/locks выявляется финальной проверкой §5.

После закрытия повтор со старым JWT → `401/session_closed`,
после удаления cookie → `401/missing_session_cookie`. Время closed_at
не меняется. Это идемпотентный эффект с разными статусами `204→401`.

Logout-401 завершает локальный credential-контекст, но не доказывает
новую запись closed_at. Удаление cookie само по себе также не является
серверным отзывом. Пригодная сессия неактивного владельца закрывается
с commit→204; последующая реактивация не делает этот JWT пригодным.
Закрытие не выдаёт доступа к `/account/me` до или после реактивации.

### 6.3. Обязательные результаты гонок

| Сценарий | Результат |
| --- | --- |
| Два Logout пригодной сессии, срок не истекает, БД исправна | Один commit/204, второй после перечитывания — 401/session_closed; исходный closed_at один и неизменен |
| Auth коммитит продление первым | Logout закрывает актуальную продлённую запись, не откатывая last_used_at/expires_at |
| Logout коммитит первым | Auth после locks видит closed_at, даёт 401 и не продлевает/восстанавливает запись |
| Срок наступил во время verify или ожидания locks | 401/session_expired; Logout не закрывает и не продлевает |
| Владелец стал неактивным до финальной проверки | При остальных выполненных условиях close, commit→204; аккаунт не активируется |
| Владелец удалён до финальной проверки | 401/session_not_found; каскадное удаление baseline не считается записью Logout |
| Бизнес-запрос прошёл Auth до закрытия | Может завершиться после Logout; его отмена и rollback не обещаются |
| Commit выполнен, ответ потерян | Запись закрыта; без ответа нельзя объявить HTTP-успех. Явный повтор со старым JWT/без cookie → 401 и удаление cookie |
| Подтверждение commit потеряно | Ошибка без удаления cookie при доставке ответа; результат БД неизвестен; только ручной повтор |

Новая аутентификация после commit закрытия обязана отказать. Auth,
начавшийся раньше, но дошедший до финальной проверки после закрытия,
также не может продлить сессию. Ранее завершённая Auth-проверка
не отзывается задним числом.

### 6.4. Временные бюджеты и браузерные гонки

- Proxy upstream timeout — **15 000 мс** от запуска upstream-запроса
  до завершения чтения ответа; до этого успешный ответ не отправляется
  браузеру. Timeout → `504/upstream_timeout`, иная ошибка связи →
  `502/upstream_failure`, без изменения cookie, если соединение доступно.
- UI timeout — **20 000 мс** от отправки Logout до получения/чтения
  результата. Это бюджет ожидания, не SLA завершения PostgreSQL.
  Более ранний ответ proxy не требует ожидать все 20 секунд.
- Abort, `502/504`, обрыв соединения или завершение клиентской попытки
  не доказывают отмену сервера/rollback. Жёсткий DB timeout контрактом
  не задаётся; после timeout возможны перекрывающиеся серверные операции.
- Автоматических повторов UI/proxy нет, включая `details.retryable`.
  Повторный POST — только явное действие пользователя.
- В одной вкладке сериализуются **клиентские ожидания** login/logout:
  не более одного, без автоматической очереди. Сторонний protected-401
  может очистить UI, но не освобождает занятую попытку Logout до её
  завершения/timeout. Новый login после timeout допустим, без обещания,
  что прежний серверный Logout уже завершился.
- Поколения авторизации/ID попыток относятся к UI. Старый callback
  не восстанавливает очищенную авторизацию и не меняет новое состояние,
  но браузер применяет Set-Cookie независимо от callback.
- Межвкладочная координация, немедленный broadcast и polling не требуются.
  Позднее удаление cookie может затронуть credential нового login
  другой вкладки или после timeout в той же вкладке. Абсолютная сохранность
  новой cookie не гарантируется. **Новая независимая серверная сессия
  этим Logout не закрывается.** Другая вкладка обнаруживает закрытие
  общей сессии при следующем protected-401/reload.

Commit, доставка HTTP, применение cookie и очистка UI не составляют
общую транзакцию. Backend не усиливает принятые CONTRACT.md §7–8 гарантии.

## 7. Архитектура и будущая актуализация документации

Domain хранит команду close, инварианты, общие ошибки и порты.
Application координирует сценарий через доменные интерфейсы,
Infrastructure обеспечивает явный async ORM I/O, refresh актуального
состояния и согласованные locks. Presentation отвечает за HTTP,
валидацию, CSRF, DI, OpenAPI, mapper и cookie. Зависимости направлены
к ядру; domain/application не импортируют FastAPI/SQLAlchemy.

Будущая реализация соблюдает правила именования/DI и Python-кодстайл
`agent-rules/`, включая dataclasses slots/kw_only, типизацию,
70 символов строки и отсутствие искусственной схемы JSON для `204`.

После сверки V2 обеих команд и **отдельного разрешения реализации**
в план должны войти:

1. OpenAPI: маршрут, cookie-security без обычного Auth DI, CSRF header,
   нулевое тело, 204 без схемы JSON, 400/401/403/405/ошибки, Allow/no-store.
2. `docs/endpoints/auth.md`: полный Logout-контракт группы auth.
3. `docs/auth.md`: отдельный сценарий без продления, повторы, commit,
   согласованная топология и границы конкуренции.
4. `docs/entities/session.md`: close и различие пригодности для Auth/Logout.
5. `docs/entities/user.md` и соответствующий контекст `agent-rules/`:
   узкое исключение ADR-07 для собственной сессии неактивного владельца,
   без ослабления обычного Auth/RBAC.
6. `docs/repositories.md`/`docs/security.md` при добавлении сценария:
   общая транзакция Logout, locks и использование существующих портов.
7. Совместная проверка реального Node.js proxy и HTTPS-cookie с FE;
   сопоставление с будущей frontend-документацией по CONTRACT.md.

Эти обновления, код и тесты в задачу создания V2 не входят.

## 8. Backend acceptance criteria

Это план будущих проверок, не отчёт о тестах и не разрешение их писать.
Если не проверяется конкретный отказ, запрос, CSRF и Origin корректны,
хранилище исправно и сессия неожиданно не истекает.

| ID | Проверяемое требование | Будущий уровень |
| --- | --- | --- |
| BE-01 | user/moderator/admin: только предъявленная пригодная сессия закрыта; после commit ровно 204, ноль байт, no-store, без Location. Остальные поля/сессии не изменены | API + PostgreSQL integration |
| BE-02 | Неактивный владелец, в том числе ставший неактивным во время verify: close→commit→204. Аккаунт не активирован, срок не продлён, после реактивации старый JWT даёт 401 | PostgreSQL integration |
| BE-03 | Отсутствующая/пустая cookie, Bearer без cookie, неверные подпись/алгоритм/claims/UUID/secret, отсутствующие сессия/владелец → соответствующий 401 и удаление cookie, без записи Logout | API + integration |
| BE-04 | Закрытая запись → 401/session_closed с исходным closed_at; после удаления cookie → 401/missing_session_cookie. Повтор не делает новый close | API + integration |
| BE-05 | now==expires_at, now>expires_at и истечение во время verify/locks → 401/session_expired без закрытия/продления | Domain + PostgreSQL integration |
| BE-06 | Нет/неверен/неоднозначен CSRF, в том числе при плохом body/query/cookie → 403 раньше их проверки; нет аутентификационного чтения сессии, Set-Cookie и записи | API + реальный proxy |
| BE-07 | С верным CSRF любое непустое тело ({}, null, пробел, валидный/повреждённый JSON) и любой query, включая пустое значение → 400 до cookie; без Set-Cookie/записи. Ноль байт с/без Content-Type проходит | API + реальный proxy |
| BE-08 | Прямой и публичный GET → 405/Allow: POST/no-store/envelope без аутентификации/изменений; HEAD без тела, OPTIONS не меняет сессии и не разрешает cross-origin credentials | API + proxy |
| BE-09 | Proxy передаёт клиентские Cookie/CSRF и статусы/Set-Cookie/no-store/Allow, не синтезирует заголовок, не очищает вход, не следует redirect и не применяет 303→201; недопустимый Origin не доходит до операции API | Совместная proxy + browser проверка |

| BE-11 | После 204 копия JWT на /v1/account/me даёт 401, другая независимая сессия работает | PostgreSQL integration |
| BE-12 | Доменный close идемпотентен, closed_at>=last_used_at при обратном сдвиге часов; immutable поля и история сохранены | Domain unit |
| BE-13 | Два конкурентных Logout при исправной БД/без истечения → один 204, один 401, один closed_at; Auth/Logout в обоих порядках не теряют свежие времена и не восстанавливают запись | Реальный PostgreSQL integration |
| BE-14 | После verify обязательны актуальные owner→session locks и финальные проверки существования/владения/проверенного hash/closed_at/срока. Блокировка владельца не мешает close; удаление → 401. Уже прошедший Auth бизнес-запрос может завершиться | Реальный PostgreSQL integration |

| BE-18 | Потеря ответа после commit оставляет запись закрытой; явный повтор со старым JWT/без cookie → 401 и удаление cookie, без нового изменения БД | Integration + совместный UI-сценарий |

## 10. Краткий diff требований V1 → V2 и остановка

| Аспект | V1 | V2 по утверждённому контракту |
| --- | --- | --- |
| Неактивный владелец | 401/inactive_user, без close | При пригодной сессии close→commit→204; Auth/RBAC остальных ресурсов без изменений |
| Body/query | Не влияют на результат | Любой непустой body/query → 400 после CSRF, до cookie; нулевое тело с Content-Type допустимо |
| CSRF | Backend-предложение | Утверждённый обязательный заголовок; неоднозначное множественное значение → 403; приоритет фиксирован |
| Deployment | Same-origin либо отдельно согласованный same-site/cross-origin | Только same-origin Node.js proxy; полный Origin, передача исходного CSRF, без CORS-альтернативы |
| Ошибки методов/публичной цепочки | Общая backend-формулировка | 405 с Allow: POST/envelope/no-store на API и proxy; HEAD/OPTIONS; контролируемые 502/504, запрет redirect-преобразования |
| Cookie | Удаление 204/401, сохранение при сбоях | Смысл сохранён; точная область Logout-401, фактические mapper/commit-ответы и межвкладочная граница закреплены |
| Verify/locks | Повторная проверка и owner→session | Явно проверяются актуальные владелец/принадлежность/hash/closed_at/срок после verify под locks; is_active не отказ |
| Клиентские гонки/таймауты | Сериализация без точных бюджетов | Локальные ожидания login/logout; 15 с proxy / 20 с UI; без автоповторов и без обещания отмены БД/сохранности новой cookie |
| Критерии | AC-01–AC-19 независимой V1 | BE-01–BE-20 и полная трассировка C-01–C-27 с распределением ответственности |

Сохранены отдельный LogoutUseCase без продления, доменная идемпотентность,
`closed_at=max(now,last_used_at)`, порядок пользователь→сессия,
commit до подтверждения, повтор `204→401`, отказ истёкшей сессии,
отсутствие влияния на другие сессии и границы уже прошедших Auth запросов.

реализации. Подготовка Backend V2 не разрешает кодогенерацию, изменение
исходников/тестов или актуализацию baseline прямо сейчас.
