# AnimeMap — Cross-review и согласование Logout V1

**Дата:** 2026-11-02  
**Статус:** cross-review завершён; ADR-01–ADR-11 утверждены пользователем с уточнениями и формализованы в §6–10.

**Текущий вывод:** разногласия LOG-01–LOG-09 разрешены на уровне общего [CONTRACT.md](CONTRACT.md). Frontend Team и Backend Team должны привести свои следующие редакции спецификаций в соответствие с ним до генерации кода. Реализация не начата и этим документом не разрешается.

**Как читать историю:** §1–5 сохраняют исходные результаты cross-review, рекомендации и первоначальный проект. Все слова «предлагается», «на согласовании», «необходимо согласовать» в этих разделах относятся к историческому этапу. Они не описывают текущий статус. Утверждённые решения находятся в §6–10, окончательные нормативные требования — в CONTRACT.md. При расхождении исторического текста с ними применяется утверждённый контракт.

**Исходный вывод cross-review:** спецификации совпадали по основному HTTP-сценарию, но не были готовы к совместной реализации из-за CSRF-заголовка, proxy-контракта, гонок с новым входом, семантики `401` и приоритетов событий UI. Исходный код, тесты и спецификации при review не изменялись.

### Что уже совпадает

Между UI §6 и BE §3–6 **нет разногласия** по следующим положениям:

| Аспект | Совпадающее предложение |
|---|---|
| Метод и путь | `POST /v1/auth/logout` |
| Нормальный запрос | Без тела и идентификаторов пользователя/сессии |
| Успех | `204 No Content`, без JSON и редиректа |
| Серверный эффект | Закрыть только сессию из предъявленной cookie |
| Подтверждение | Успешный commit должен предшествовать `204` |
| Повтор | После успешного закрытия — `401`, а не повторный `204` |
| Истечение | `now >= expires_at` означает недействительную сессию |
| Идемпотентность | Повтор не меняет исходное `closed_at` |
| Конкуренция с Auth | Закрытая сессия не продлевается и не восстанавливается |
| Уже аутентифицированные операции | Могут завершиться после Logout |
| Ошибка сети/commit | Не является подтверждением успешного выхода |
| Права | Одинаковые условия для `user`, `moderator`, `admin` |

Это соответствует baseline `docs/auth.md`, особенно разделам «Проверка каждого запроса» и «Выход и истечение».

**Идемпотентность эффекта не требует одинакового HTTP-статуса.** Последовательность `204 → 401` сама по себе не является противоречием.

## 2. Обнаруженные проблемы LOG-01–LOG-09 — исходные результаты

Серьёзность:

- **Высокая** — блокирует интеграцию либо нарушает ожидаемые гарантии сессии/авторизации.
- **Средняя** — оставляет неоднозначный контракт, UX или критерий приёмки.

Отдельно отмечены прямые расхождения и пробелы: отсутствие требования в одной спецификации не всегда означает противоречащее требование.

### LOG-01. Обязательный CSRF-заголовок отсутствует в UI-контракте

**Серьёзность: высокая. Тип: несовместимость описанных запросов.**

- **UI:** §6 задаёт cookie-запрос без требования `X-AnimeMap-Logout`; US-01 и AC-02 ожидают успешный выход по этому контракту.
- **BE:** §3.1, §7 и AC-08 требуют `X-AnimeMap-Logout: 1`. Без него возвращается `403`, причём раньше проверки cookie.

UI-запрос, составленный только по своей спецификации, будет отклонён Backend.

**Рекомендация:** согласовать предложенный BE заголовок и явно включить его в общий запрос. Зафиксировать, что это CSRF-барьер, а не аутентификация: JWT и серверная проверка сессии остаются обязательными. Прокси должен передавать заголовок клиента, не подставляя его самостоятельно.

**Изменить после утверждения:**

- **UI:** §5–6, AC-02, AC-09, §9 — заголовок, семантика CSRF-отказа.
- **BE:** §3.1, §7, AC-08–09, §10 — заменить статус предложения согласованной политикой, закрепить проверку через реальный прокси.

### LOG-02. Не определён единый публичный контракт прокси и топология V1

**Серьёзность: высокая. Тип: интеграционный пробел и неоднозначность границы API.**

- **UI:** §1, §6 требуют same-origin frontend-прокси и `credentials: 'same-origin'`.
- **BE:** §7 допускает same-origin proxy либо отдельно согласованный same-site deployment; описывает также cross-origin credentials/CORS и `GET → 405`.
- **Baseline:** `frontend/server/proxy.mjs`:
  - не пропускает Logout;
  - создаёт upstream-заголовки заново и не передаёт `X-AnimeMap-Logout`;
  - возвращает `404` для метода/маршрута вне allowlist, поэтому браузерный GET не получит обещанный BE `405`;
  - проверяет Origin POST по `host`, а не по полному origin.

Общее ожидание «прокси пропускает маршрут» недостаточно для приёмки.

**Рекомендация:** для V1 утвердить конкретную схему браузер → same-origin frontend-прокси → API. Зафиксировать публичный ответ на неподдерживаемый метод, прохождение заголовков и политику Origin. Cross-origin deployment считать отдельным решением с конкретным allowlist, если он нужен.

**Изменить:**

- **UI:** §6, §9, AC-15 — полный proxy-контракт и публичные статусы.
- **BE:** §3.1, §7, AC-09/17, §10 — топология, область обещания `405`, доверенные origin и ответственность прокси.

### LOG-03. Игнорирование позднего ответа не защищает новую cookie

**Серьёзность: высокая. Тип: несовместимость UX-гарантии с недостаточным механизмом её обеспечения.**

- **UI:** US-04, §5, AC-07/10/12 требуют игнорировать позднее завершение старой попытки и не повреждать состояние нового входа.
- **BE:** §6.3 прямо признаёт, что поздний `Set-Cookie` Logout может удалить cookie нового login, и требует сериализации login/logout.
- **UI:** не задаёт соответствующий протокол сериализации; US-06 исключает обязательную мгновенную межвкладочную синхронизацию.

Пример:

1. Logout со старой cookie выполняется долго.
2. UI прекращает ожидание либо другая вкладка выполняет login.
3. Login устанавливает новую `session_token`.
4. Поздний Logout отвечает `204` или `401` с удаляющим `Set-Cookie`.
5. Браузер удаляет новую cookie независимо от того, игнорирует ли JavaScript результат.

BE корректно закрывает только старую серверную сессию, но браузер теряет credential новой.

**Рекомендация:** разделить две гарантии:

- устаревшие ответы не изменяют состояние React — поколения авторизации/идентификаторы попыток;
- конкурирующие auth-ответы не повреждают cookie — отдельная политика сериализации.

Предлагается сериализовать auth-операции как минимум внутри вкладки и отдельно утвердить межвкладочную гарантию. Если строгая сохранность нового login между вкладками обязательна, нужен согласованный механизм координации; одного игнорирования Promise недостаточно.

**Изменить:**

- **UI:** US-03/04/06, §4–5, AC-07/10/12/14 — правила нового входа после таймаута, область координации и предел гарантии.
- **BE:** §6.3, §7, §10 — точное значение «сериализовать», остаточная гонка и сквозные критерии её проверки.

### LOG-04. Не определён приоритет Logout, чужого `401` и нового входа

**Серьёзность: высокая. Тип: пробел машины состояний.**

- **UI:** §4 сохраняет `pending`, блокирует действия и требует оставаться на исходном экране после ошибки.
- **UI:** US-06 и существующие обработчики истечения допускают очистку аккаунта по `401` другого защищённого запроса.
- **BE:** §6.3 допускает завершение ранее запущенных бизнес-запросов и требует сериализации login/logout.

Не описано, что произойдёт, если во время Logout другой запрос вернул `401`, UI открыл вход, а затем Logout вернул `503` или завершился после нового login.

Без правила приоритета старый callback может восстановить экран, показать чужую ошибку или сбросить новую авторизацию.

**Рекомендация:** зафиксировать поколение авторизации и независимый жизненный цикл Logout-попытки:

- событие старого поколения не изменяет новое;
- переход в неавторизованное состояние не отменяется последующей ошибкой старого Logout;
- `failed` сохраняет исходный экран только пока текущее поколение ещё локально авторизовано;
- доступность нового login определяется решением LOG-03.

**Изменить:**

- **UI:** US-02–04, §4–5, AC-06/07/10 — приоритеты событий и дополнительные переходы.
- **BE:** §6.3, §10 — требования к клиентской координации и соответствующие интеграционные сценарии.

### LOG-05. Удаление cookie на `401` остаётся несогласованным

**Серьёзность: средняя. Тип: открытый вопрос одной команды уже превращён в требование другой.**

- **UI:** §6, строки 211–213, и §9 оставляют удаление недействительной cookie на `401` на согласование.
- **BE:** §3.3, §5 и §7 требуют удаления cookie на каждом logout-`401`, включая отсутствие cookie.
- Обе команды согласны, что `401` не доказывает новое закрытие записи.

**Рекомендация:** принять политику BE: удалять cookie на `204` и logout-`401`; сохранять её на `403` и сбоях. Удаление должно иметь host-only scope, `Path=/`, пустое значение, `Max-Age=0`, истёкший `Expires`, `Secure; HttpOnly; SameSite=Lax`.

При этом последствия позднего удаления должны быть согласованы по LOG-03.

**Изменить:**

- **UI:** §6, §9, AC-05/08/15 — обязательное удаление на `401`, точный scope.
- **BE:** §3.3, §7, AC-17/18 — явно связать cookie-политику с согласованной политикой конкуренции.

### LOG-06. `401` не гарантирует необратимый отзыв серверной сессии

**Серьёзность: средняя. Тип: неоднозначность гарантии и пользовательского сообщения.**

- **UI:** US-02 и §5 показывают «Сессия истекла» для отсутствующей, закрытой и любой иной недействительной сессии.
- **BE:** §3.3 включает `inactive_user`, не изменяет БД; §5 допускает завершение локального входа после `401`.
- **Baseline:** блокировка пользователя запрещает использование сессий без удаления; активность проверяется при каждом запросе.

Если владелец неактивен, Logout вернёт `401`, но `closed_at` останется пустым. Если пользователя активируют до истечения срока, сохранённая копия корректного JWT потенциально снова сможет пройти аутентификацию.

Это **не нарушение заявленной BE гарантии `204`**. Это граница, которую необходимо явно назвать: завершение локального входа после `401` не равно постоянному отзыву записи.

**Рекомендация:** сохранить baseline-семантику V1, но:

- использовать для общего `401` сообщение «Сессия недействительна. Войдите снова.»;
- явно ограничить гарантию необратимого отзыва успешным закрытием;
- отдельно утвердить, нужен ли Logout для неактивного владельца с фактическим закрытием записи. Это потребовало бы изменения действующих правил.

**Изменить:**

- **UI:** US-02, §4–6, AC-05 — сообщение и граница гарантии.
- **BE:** §3.3, §5–6, §10 — последствия `inactive_user` и возможной реактивации.

### LOG-07. «Без тела/query» не определяет обработку нарушений запроса

**Серьёзность: средняя. Тип: неоднозначность входного контракта.**

- **UI:** §6 задаёт запрос без тела и query, но не определяет реакцию на их наличие.
- **BE:** §3.1 говорит, что дополнительные тело и query не влияют на результат.
- В baseline другие auth-запросы запрещают неизвестные поля, но это автоматически не распространяется на новый endpoint без модели тела.

Неясно, должны ли `?session_id=...`, `{}`, произвольный JSON или повреждённое тело игнорироваться либо давать `400`.

**Рекомендация:** явно выбрать политику. Для строгого SDD-контракта предлагается `400` при непустом теле или любых query-параметрах, без изменения БД и удаления cookie. Наличие `Content-Type` при пустом теле само по себе не считать ошибкой: текущие клиент и прокси его устанавливают.

**Изменить:**

- **UI:** §6 и критерии HTTP-интеграции — допустимый запрос и отказ.
- **BE:** §3.1/3.3, AC — заменить игнорирование строгой валидацией, если предложение утверждено; определить порядок после CSRF-проверки.

### LOG-08. Единый формат ошибок не действует на всей браузерной цепочке

**Серьёзность: средняя. Тип: несовместимость общего обещания с baseline-прокси.**

- **UI:** §6 ожидает существующий `error/message/details`.
- **BE:** §3.3 и AC-18 требуют общий формат фактических ошибок.
- **Baseline:** proxy-ответы `403/404/413/502/504` содержат только `message`; стандартные routing-ошибки также не покрыты показанным domain mapper.

Не определено, относятся ли требования к backend-обработчику или ко всему публичному `/v1/auth/logout`.

Дополнительно текущий API-клиент принимает любой `2xx` и преобразует отсутствие/невалидность JSON в `{}`. Для Logout необходима проверка именно `204`, как уже требует UI §5.

**Рекомендация:** унифицировать контролируемые ошибки API и frontend-прокси. В UI сохранить обработку по статусу с безопасным fallback для ответа без envelope. Не трактовать инфраструктурный отказ как logout-`401`; успешным считать только согласованный `204`.

**Изменить:**

- **UI:** §5–6, AC-09/15 — область envelope, fallback, проверка точного успеха.
- **BE:** §3.3, §8–9 — routing/proxy-ошибки, границы ответственности и контракт публичной цепочки.

### LOG-09. Таймаут UI совпадает с upstream-таймаутом прокси

**Серьёзность: средняя. Тип: несогласованные временные условия.**

- **UI:** §5 и AC-07 предлагают 15 секунд на клиентскую попытку.
- **BE:** §6.3 признаёт независимость commit и доставки ответа, но не задаёт бюджет ожидания/блокировок.
- **Baseline:** frontend-прокси использует `AbortSignal.timeout(15000)` для upstream.

Таймеры запускаются в разные моменты. UI может завершить ожидание раньше получения сформированного прокси `504`. После ручного повтора серверные операции предыдущей попытки ещё могут выполняться.

**Рекомендация:** согласовать бюджет UI/proxy/backend. Предпочтительно оставить запас клиентского ожидания относительно proxy-timeout, если важно получать его `504`. Если 15 секунд UI — жёсткое продуктовое требование, upstream-бюджет должен учитывать этот предел. В любом варианте таймаут означает неопределённый результат, а не rollback.

**Изменить:**

- **UI:** §5, AC-07/08, §9 — начало отсчёта, прекращение ожидания, повтор.
- **BE:** §6, §9–10 — поведение после разрыва/таймаута, ожидание блокировок и сквозные критерии.
- В обеих спецификациях — ссылка на согласованный proxy-timeout.

## 3. Первоначальные рекомендации ADR — история, не текущие решения

| Решение | Рекомендация | Связанные проблемы |
|---|---|---|
| **ADR-01. Базовый HTTP-контракт** | `POST /v1/auth/logout`, пустой запрос, `204` без тела/редиректа; повтор — `401` | Базовое совпадение |
| **ADR-02. CSRF** | Обязательный `X-AnimeMap-Logout: 1`, проверка раньше аутентификации; прокси не добавляет его самостоятельно | LOG-01 |
| **ADR-03. Топология V1** | Same-origin frontend-прокси; явная политика Origin и публичный `405` | LOG-02 |
| **ADR-04. Cookie** | Удаление на `204/401`, сохранение на `403` и ошибках | LOG-05 |
| **ADR-05. Конкуренция auth-операций** | Сериализация внутри вкладки; отдельно выбрать строгую межвкладочную координацию либо явно принять остаточную гонку | LOG-03 |
| **ADR-06. Приоритет событий UI** | Поколение авторизации и ID попытки; старое событие не меняет новый вход и не восстанавливает очищенный UI | LOG-04 |
| **ADR-07. Граница `401`** | Локально завершать вход без обещания отзыва записи; нейтральное сообщение. Возможность закрытия сессии неактивного владельца решить отдельно | LOG-06 |
| **ADR-08. Лишний вход** | Непустое тело/query → `400`; пустое тело с `Content-Type` допустимо | LOG-07 |
| **ADR-09. Ошибки публичной цепочки** | Общий envelope для контролируемых backend/proxy-ошибок; fallback в UI | LOG-08 |
| **ADR-10. Таймауты** | Согласовать численные бюджеты и прекращение ожидания; не приравнивать timeout к отмене commit | LOG-09 |
| **ADR-11. Серверная транзакция** | Отдельный LogoutUseCase без обычного Auth-продления; блокировки пользователь → сессия; commit до успеха | Подтверждение общего предложения |

## 5. Первоначальный проект контракта — история, заменён CONTRACT.md

**Статус: на согласовании.** Пункты, затрагивающие ADR выше, становятся обязательными только после утверждения пользователем.

### Запрос

```http
POST /v1/auth/logout HTTP/1.1
Cookie: session_token=<jwt>
X-AnimeMap-Logout: 1
```

- Браузер обращается к same-origin frontend-прокси с `credentials: 'same-origin'`, `cache: 'no-store'`.
- Тело и query отсутствуют. `Content-Type` не требуется, но допустим при пустом теле.
- Предлагаемая строгая политика: непустое тело/query → `400`.
- Текущая сессия определяется исключительно cookie; `Authorization` не заменяет её.
- Все активные пользовательские роли имеют одинаковый доступ к собственной сессии.
- CSRF-проверка предшествует валидации входа и проверке cookie.
- Другие методы не изменяют сессию. Предлагаемый публичный результат для GET — `405`.
- OPTIONS, если нужен выбранной топологии, не проверяет пользовательскую сессию и не изменяет её.

### Успех

```http
HTTP/1.1 204 No Content
Cache-Control: no-store
Set-Cookie: session_token=; Path=/; Max-Age=0; Expires=Thu, 01 Jan 1970 00:00:00 GMT; Secure; HttpOnly; SameSite=Lax
```

`Domain` отсутствует: удаляется host-only cookie того же публичного хоста, на котором браузер получил login-cookie.

**Гарантии `204`:**

1. Закрытие сессии из предъявленного JWT успешно закоммичено.
2. Изменён только `closed_at`; времена использования/истечения не продлеваются.
3. Повторное закрытие не меняет исходный `closed_at`.
4. После commit новая аутентификация этим JWT отклоняется.
5. Конкурентный Auth не восстанавливает закрытую запись.
6. Другие независимые сессии не закрываются.
7. Уже прошедшая аутентификацию бизнес-операция может завершиться.
8. Ответ не содержит JSON, токена, срока сессии или редиректа.

Сервер гарантирует отправку команды удаления cookie; её доставка и применение браузером не входят в транзакцию PostgreSQL.

### Ошибки и повторы

| Условие | Ответ | Cookie | Серверный эффект |
|---|---|---|---|
| Нет/неверен CSRF-заголовок | `403 / access_denied`, `reason=csrf_check_failed` | Сохранить | Без изменения |
| Непустое тело/query — предложенная политика | `400 / bad_request` | Сохранить | Без изменения |
| Cookie отсутствует/пуста | `401 / authentication_failed` | Удалить | Без изменения |
| JWT некорректен, секрет неверен, сессия отсутствует | `401 / authentication_failed` | Удалить | Без изменения |
| Сессия закрыта | `401`, обычно `reason=session_closed` | Удалить | `closed_at` неизменен |
| Сессия истекла, включая равенство срока | `401`, обычно `reason=session_expired` | Удалить | Не закрывать и не продлевать |
| Владелец неактивен | `401`, `reason=inactive_user` | Удалить | По предложению BE — не закрывать запись |
| PostgreSQL недоступен | `503 / service_unavailable` | Сохранить | Нет подтверждения закрытия |
| Повреждённый сохранённый Argon2-хэш | `400 / bad_request` | Сохранить | Нет подтверждения закрытия |
| Иные backend-ошибки | По `docs/errors.md` | Сохранить | Откат незавершённого изменения, если результат известен |
| Proxy/network timeout, `502/504`, обрыв ответа | Ошибка/неопределённый результат | Получение заголовков нельзя предполагать | Commit мог состояться |

Все контролируемые ответы — с `Cache-Control: no-store`. Контролируемые ошибки API/прокси предлагается возвращать как:

```json
{
  "error": "authentication_failed",
  "message": "Authentication failed",
  "details": {
    "reason": "session_closed"
  }
}
```

UI не зависит от текста `message` и полного приоритета причин. Порядок CSRF-проверки является частью контракта.

### Серверная граница аутентификации

- Отдельная проверка Logout без `AuthUseCase.authenticate()` и `SessionEntity.use()`.
- Проверяются подпись, claims, сессия, секрет и владелец.
- После дорогостоящего verify выполняется повторная проверка актуального состояния под блокировками **пользователь → сессия**, по свежему UTC-времени.
- Закрытие и его сохранение образуют одну транзакцию.
- Flush не является достаточным основанием для `204`.
- Неизвестный результат commit не маскируется под успех или гарантированный rollback.
- HTTP, cookie и CSRF остаются в presentation; доменная команда закрытия не знает о них.

### Реакция UI

| Результат | Поведение |
|---|---|
| Только согласованный `204` | Очистить защищённые данные, открыть `#/login`, показать «Вы вышли из аккаунта.» |
| Logout-`401` | Очистить UI, открыть вход; предлагаемое сообщение «Сессия недействительна. Войдите снова.»; не утверждать новое закрытие записи |
| `403`, прочие ошибки, неожиданный `2xx` | Показать ошибку Logout; не подменять её успехом |
| Сеть/timeout | Сообщить, что выход не подтверждён; предложить ручной повтор |
| Ошибка при уже очищенной авторизации | Не восстанавливать аккаунт или защищённый экран |
| Поздний ответ старого поколения | Не изменять новое состояние авторизации |

В `pending` блокируются повтор Logout и новые защищённые действия. Автоматических повторов нет. После потери ответа ручной повтор может вернуть `401` — это штатный исход идемпотентного эффекта.

**До утверждения остаются открытыми:** область сериализации между вкладками, безопасность нового login после прекращения ожидания и численные бюджеты таймаутов.

**Конец исторического результата:** на этом этапе ожидалось согласование ADR-01–ADR-11. Ниже зафиксировано последующее утверждение пользователем.

### 6.1. Существенные отличия от исторических рекомендаций

1. **ADR-07 изменяет исходное BE-предложение и §5 этого review:** `inactive_user` больше не является основанием отказа именно для Logout. Это узкое исключение из обычного запрета операций неактивного пользователя, а не ослабление Auth или RBAC остальных ручек.
2. **ADR-05:** межвкладочная координация не остаётся открытым вопросом — пользователь исключил её из обязательств V1. Остаточная гонка принята, а не устранена.
3. **ADR-10:** вместо исторических 15 секунд UI и открытого бюджета закреплены 20 секунд UI и 15 секунд upstream.
4. **ADR-08:** игнорирование дополнительных тела/query из BE §3.1 заменено обязательным `400`.
5. **ADR-03:** альтернативный same-site/cross-origin deployment из BE §7 не входит в V1.

### 6.2. Проверка согласованности решений

Прямых противоречий между утверждёнными ADR не выявлено. Есть важные границы трактовки:

- Сериализация внутри вкладки относится к **клиентским попыткам**. Их завершение по timeout не является подтверждением завершения серверной операции. Утверждать отсутствие серверного перекрытия после timeout нельзя. См. CONTRACT.md §7.
- ADR-07 конфликтует с обобщёнными формулировками baseline `docs/auth.md` о неактивном владельце и `docs/entities/user.md` об отказе во всех операциях. Пользователь явно утвердил исключение только для закрытия собственной сессии; остальные правила не меняются. Backend Team должна отразить это в своей V2 и плане актуализации baseline.
- Приоритет CSRF относится к POST перед валидацией входа и сессии. GET получает `405` без аутентификации; proxy-Origin может отклонить POST раньше обращения к API. Это не превращает GET или Origin-проверку в проверку сессии.
- Команда удаления cookie, клиентское состояние и commit БД не составляют общую транзакцию. ADR-04 не отменяет ограничения ADR-05/10.

## 8. Осознанные ограничения и остаточные риски V1

1. **Общая cookie между вкладками.** Поздний logout-ответ одной вкладки может удалить cookie нового login другой. Сервер закрывает сессию из JWT конкретного запроса; новая независимая запись в БД не закрывается. Глобальный auth-lock и мгновенная синхронизация вкладок не требуются.
2. **Неизвестный результат после timeout/обрыва.** Даже после завершения клиентской попытки сервер мог выполнить commit или продолжить работу. Ни abort, ни 504, ни 20 секунд ожидания не доказывают rollback и не дают абсолютной защиты новой cookie.
3. **Старые данные в другой вкладке.** Очищаются при следующем защищённом ответе `401` или перезагрузке; polling и немедленная рассылка не входят в V1.
4. **Ранее аутентифицированные операции.** Могут завершиться после Logout; он не отменяет их и не откатывает изменения задним числом.
5. **Доставка cookie.** Даже после commit ответ может потеряться. Успешное закрытие в БД и фактическое удаление browser-cookie проверяются отдельно.
6. **Границы функциональности.** Нет logout всех устройств, refresh-токенов, новых хранилищ отзыва, управления сессиями, отдельного cross-origin deployment или автоматических повторов.

Эти ограничения не являются незакрытыми LOG-противоречиями: они явно приняты пользователем. Новое требование устранить их потребует отдельного решения.

1. **§1–4, AC-01/07/19:** разрешить закрытие подтверждённой незакрытой/неистёкшей сессии неактивного владельца. Удалить logout-ветку `401/inactive_user`. При блокировке во время verify закрытие остаётся допустимым; при удалении владельца — 401.
2. **§3.1/3.3:** вместо игнорирования тела/query — 400 после CSRF и до проверки cookie; пустое тело с Content-Type допускается. Согласовать полный error-envelope с proxy.
3. **§4–6:** отдельный LogoutUseCase/DI, JWT/secret, без обычного Auth/use/продления, пользователь→сессия, актуальное перечитывание, повторная проверка срока/закрытия и владения; не проверять is_active как запрет Logout.
4. **§5–6, AC-02/10–16:** сохранить доменную идемпотентность, closed_at>=last_used_at, неизменность остальных полей, commit до HTTP и корректную ошибку commit без удаления cookie.
5. **§6.3–7:** удалить cross-origin/same-site альтернативу из V1; уточнить локальную сериализацию, принятый межвкладочный риск, 15/20 секунд, неизвестный результат и границы уже аутентифицированных запросов.
6. **§3/7–9:** cookie/no-store на фактических ответах mapper, 401 и ошибки завершения транзакции; GET→405 и отсутствие редиректа; секреты не включать в ответ/логи.
7. **§8–10:** включить план будущей актуализации OpenAPI, docs/endpoints/auth.md, docs/auth.md, документации Session и узкого исключения для неактивного User в baseline/agent-rules. Сейчас эти файлы не менять.
8. Связать критерии V2 с C-01–C-27 CONTRACT.md, в том числе реальный PostgreSQL, HTTPS-браузер и Node.js proxy. Обе команды должны сверить V2 с одним CONTRACT.md до отдельного разрешения реализации.
