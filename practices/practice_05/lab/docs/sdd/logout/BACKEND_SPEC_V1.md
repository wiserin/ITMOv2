# AnimeMap — Backend Logout Specification V1

- **Версия:** 1.0.
- **Статус:** самостоятельное предложение Backend Team для совместного согласования.
- **Этап SDD:** спецификация требований и контракта; реализация не разрешена до согласования обеих команд.
- **Область:** завершение текущей серверной сессии через HTTP API.
- **Независимость:** подготовлена без использования спецификации Frontend Team.

Примечание о проверке: после создания этого документа поисковый
инструмент непреднамеренно вернул также заголовки `UI_SPEC_V1.md`.
Содержимое её разделов не изучалось; backend-решения по этой выдаче
не корректировались.

Слова «должен» и «запрещено» обозначают требования предлагаемой V1,
а не утверждение о наличии такой реализации в текущем коде.

## 1. Цель и границы

Пользователь завершает текущую сессию. После подтверждённого выхода
предъявление копии её JWT больше не позволяет аутентифицироваться.
Браузер получает серверную команду удаления HttpOnly cookie.
Остальные сессии того же пользователя продолжают работать.

В V1 не входят logout всех устройств, выбор чужой сессии по ID,
refresh-токены, ротация JWT, изменение пароля, фоновые задачи очистки,
реализация UI и отмена уже аутентифицированных бизнес-запросов.

## 2. Основания и совместимость

Изучены следующие источники текущего backend-контракта:

- `backend/app/domain/entities/session.py`;
- `backend/app/application/usecases/auth.py`;
- `backend/app/domain/repositories/session.py`;
- `backend/app/presentation/api/routes/auth/`;
- `docs/auth.md`;
- `agent-rules/AGENTS.md`, `agent-rules/naming.md`, `agent-rules/codestyle.md`.

Дополнительно проверены `docs/entities/session.md`, `docs/errors.md`,
адаптер SessionRepository, управление PostgreSQL-транзакциями,
cookie DI и адаптеры JWT/Argon2id.

### 2.1. Уже существующие ограничения

1. Один JWT соответствует одной серверной сессии. JWT содержит
   `jti` (UUIDv4), `secret`, `iat`; подписывается EdDSA/Ed25519.
   Фиксированного `exp` нет; действительность проверяется по БД.
2. В сессии хранится только `secret_hash`. Открытый секрет не должен
   попадать в сущность, репозиторий, БД, логи или JSON-ответ.
3. Токен принимается только из `session_token` cookie. Заголовок
   `Authorization` не заменяет cookie.
4. Сессия пригодна для аутентификации, если `closed_at IS NULL`,
   `now < expires_at` и владелец активен. При равенстве времени срок истёк.
5. Обычная аутентификация продлевает скользящий срок. AuthUseCase
   блокирует сначала пользователя, затем сессию и отдельно коммитит
   продление до выполнения бизнес-сценария.
6. `docs/auth.md`, раздел «Выход и истечение», задаёт идемпотентность
   доменного закрытия, но отказ аутентификации при повторном HTTP-запросе
   с уже недействительной сессией. V1 сохраняет это различие.

### 2.2. Что предстоит добавить после согласования

В auth-роутере сейчас подключены только login/register.
У SessionEntity есть `ensure_usable()` и `use()`, но ещё нет доменной
команды закрытия. Имеющихся `get_by_id(for_update=True)` и `update()`
репозитория достаточно для проектируемого сценария; физическое удаление
через `delete()` не является logout. Изменение схемы БД не требуется.

## 3. HTTP-контракт

### 3.1. Запрос

```http
POST /v1/auth/logout HTTP/1.1
Cookie: session_token=<jwt>
X-AnimeMap-Logout: 1
```

- Имя маршрута: `auth_logout`, группа OpenAPI: `auth`.
- JSON-тело, query- и path-параметры отсутствуют. ID сессии,
  пользователя и временные метки клиентом не задаются.
- Дополнительное тело и query-параметры не используются для выбора
  сессии и не влияют на результат. Клиент должен отправлять пустое тело.
- `Content-Type` для пустого тела не требуется.
- `X-AnimeMap-Logout: 1` обязателен для защиты от браузерного CSRF
  (раздел 7); это публичная константа, не секрет и не токен.
- Все роли активных пользователей могут завершить собственную
  действительную сессию; отдельное административное право не нужно.
- GET и другие неподдерживаемые методы не закрывают сессию;
  для GET возвращается `405 Method Not Allowed`.

### 3.2. Успех

```http
HTTP/1.1 204 No Content
Cache-Control: no-store
Set-Cookie: session_token=""; Path=/; Max-Age=0; Expires=Thu, 01 Jan 1970 00:00:00 GMT; Secure; HttpOnly; SameSite=Lax
```

`204` возвращается только после успешного commit закрытия в PostgreSQL.
Тело отсутствует: ни `{}`, ни `null`, ни JWT, ни сведения о сроке сессии.
Редиректа нет. Порядок атрибутов Set-Cookie и кавычки пустого значения
не являются значимыми частями контракта.

### 3.3. Ошибки и cookie

Все ответы обработчика logout имеют `Cache-Control: no-store`.
Ошибки используют существующий формат `ErrorResponse`:

```json
{
  "error": "authentication_failed",
  "message": "Authentication failed",
  "details": {"reason": "session_closed"}
}
```

`message` человекочитаемое; клиентская логика не должна зависеть от его текста.

| Условие | HTTP / error | details.reason | Удалить cookie | Изменение БД |
| --- | --- | --- | --- | --- |
| Cookie отсутствует или пуста | 401 / authentication_failed | missing_session_cookie | Да | Нет |
| Неверная подпись, алгоритм или payload JWT | 401 / authentication_failed | invalid_token | Да | Нет |
| Сессия или её владелец отсутствует | 401 / authentication_failed | session_not_found | Да | Нет |
| Сессия уже закрыта | 401 / authentication_failed | session_closed | Да | Нет |
| Сессия истекла | 401 / authentication_failed | session_expired | Да | Нет |
| Секрет не соответствует хэшу | 401 / authentication_failed | invalid_secret | Да | Нет |
| Владелец неактивен | 401 / authentication_failed | inactive_user | Да | Нет |
| Нет обязательного CSRF-заголовка либо значение неверно | 403 / access_denied | csrf_check_failed | Нет | Нет |
| PostgreSQL недоступен, включая сбой commit | 503 / service_unavailable | По общему mapper | Нет | Нет подтверждённого закрытия |
| Прочая доменная/внутренняя ошибка | По `docs/errors.md` | По общему mapper | Нет | Откат незавершённой транзакции |

CSRF-проверка выполняется раньше чтения и проверки токена; при её отказе
применяется именно строка `403`, даже если cookie тоже недействительна.
При нескольких дефектах токена/сессии возвращается первая обнаруженная
ошибка; приоритет всех причин не является публичной гарантией.

Повреждённый сохранённый Argon2-хэш — ошибка данных, а не неверный
клиентский секрет: сохранить существующий маппинг DataFormatException
в `400 / bad_request`, не удалять cookie, не подтверждать закрытие.
Deadlock/serialization failure обрабатываются по `docs/errors.md`,
включая `details.retryable`, без преобразования в успешный выход.

На `401` удаление cookie очищает локальный недействительный credential,
но не означает, что сервер только что закрыл найденную запись.
На `503` и прочих сбоях cookie сохраняется для повторной попытки.
Если результат commit неизвестен из-за разрыва соединения, нельзя
обещать rollback: запись могла быть закрыта, но `204` не возвращается.

## 4. Серверный сценарий

Logout должен проверять те же криптографические и серверные условия,
что обычная аутентификация, **без использования и продления сессии**.

1. Presentation проверяет CSRF-заголовок и извлекает cookie.
   При отсутствии токена возвращается предусмотренный `401`.
2. LogoutUseCase проверяет JWT существующим JwtProviderPort:
   фиксированный алгоритм, подпись, набор и типы claims, UUIDv4.
3. Найти сессию по `jti`; выполнить предварительную проверку состояния.
   Недействительные сессии не изменяются.
4. Проверить `secret` через SecretManagerPort по `secret_hash`.
   JWT decode и тяжёлый Argon2id verify не блокируют event loop;
   использовать существующие адаптеры и `asyncio.to_thread`.
   Долгий verify выполняется до захвата блокировок строк.
5. В одной транзакции блокировать владельца через UserRepository,
   затем перечитать сессию через `get_by_id(..., for_update=True)`.
   Использовать актуальное состояние БД, не старый ORM snapshot.
6. Повторно проверить существование, активность владельца, закрытие
   и истечение сессии по свежему UTC-времени после получения блокировок.
   Проверенный secret_hash должен соответствовать перечитанной записи;
   по действующим инвариантам он неизменяем.
7. Вызвать доменную команду закрытия SessionEntity и сохранить результат
   через `SessionRepository.update()`. Меняется только `closed_at`.
8. Завершить транзакцию; после успешного commit отправить `204`
   и команду удаления cookie.

Нельзя подключать стандартную `AuthUseCaseDI` к logout: она возвращает
только UserDTO и уже продлевает/коммитит сессию. Нельзя предварительно
вызывать `authenticate()` или `SessionEntity.use()` для выхода.
Logout, в том числе неуспешный, не обновляет `last_used_at` и `expires_at`.

## 5. Доменное закрытие, истечение и повторы

Предлагаемая команда `SessionEntity.close(now=...)` возвращает новый
immutable объект, сохраняя правила `frozen`, `slots`, `kw_only`:

- Если `closed_at` уже задан, вернуть эквивалентное состояние,
  не менять исходное время закрытия.
- Иначе установить `closed_at = max(now, last_used_at)` с timezone-aware
  UTC-временем. Это сохраняет инвариант `closed_at >= last_used_at`
  при небольшом обратном сдвиге серверных часов.
- Не менять `id`, `user_id`, `secret_hash`, `created_at`,
  `last_used_at`, `expires_at`; не удалять запись.
- Доменное закрытие само по себе может пометить и истёкшую запись,
  не делая её пригодной к использованию. Публичный logout V1 до этой
  команды допускает только действительную сессию.

Истечение определяется условием `now >= expires_at`, даже если
`closed_at IS NULL`. Logout истёкшей сессии возвращает `401`, удаляет
cookie и не материализует закрытие в БД. Новый вход создаёт новую сессию.

Повтор HTTP logout со старым JWT возвращает `401/session_closed`;
повтор после применения удаления cookie — `401/missing_session_cookie`.
Оба варианта повторяют команду удаления cookie, не меняя БД.
Это идемпотентность эффекта, а не одинаковый HTTP-статус первого
и повторного вызовов. Клиент может завершить локальное состояние входа
после `204` или `401`; `403`, `5xx` и сетевой сбой не подтверждают выход.

## 6. Транзакционные гарантии и конкуренция

### 6.1. Граница транзакции

- Использовать общую PostgreSQL-сессию репозиториев logout.
  Commit/rollback принадлежат фабрике сессий;
  `PostgresSessionDI` со `scope="function"` завершает commit до отправки
  успешного ответа. Репозитории выполняют flush, но не commit.
- Проверки после блокировок и запись закрытия составляют одну
  атомарную операцию. Блокировки удерживаются до commit/rollback.
- Запрещено подтверждать выход после одного flush и до commit.
  При исключении откатывать незавершённые изменения; ошибка commit
  должна заменить подготовленный `204` ошибочным ответом без удаления cookie.
- PostgreSQL — единственный источник истины. Logout не зависит
  от Redis и не требует JWT blacklist или новых хранилищ.

### 6.2. Порядок блокировок

Порядок тот же, что у AuthUseCase/login: **пользователь → сессия**.
Чтение до verify не является основанием для записи без повторного
чтения под блокировкой. Нельзя сохранять устаревшую сущность,
которая восстановит `closed_at = NULL` или перезапишет свежее продление.

### 6.3. Наблюдаемые результаты гонок

| Гонка | Обязательный результат |
| --- | --- |
| Два logout одной действительной сессии | Один закрывает и получает `204`; другой после перечитывания получает `401/session_closed`. Исходное `closed_at` сохраняется |
| Auth фиксирует продление первым | Logout закрывает актуальную продлённую запись, не отменяя её времён использования |
| Logout фиксирует закрытие первым | Ожидающий Auth после блокировки видит закрытие, возвращает `401`, не продлевает сессию |
| Срок истёк во время verify/ожидания блокировки | Повторная проверка возвращает `401/session_expired`; закрытие и продление не выполняются |
| Владелец заблокирован/удалён до финальной проверки | `401`; logout не подтверждает успешное закрытие |

Точка подтверждения отзыва — commit закрытия. Любая последующая
аутентификация этого JWT обязана отказать, в том числе если началась
до commit, но ещё не завершила финальную проверку под блокировкой.
Бизнес-запрос, уже прошедший аутентификацию до закрытия, может завершиться:
logout не откатывает его задним числом.

Commit БД и доставку HTTP/cookie невозможно сделать общей транзакцией.
При потере ответа после commit сессия остаётся закрытой; повтор
со старой cookie даёт `401` и снова очищает её. При параллельном login
ответы могут приходить в разном порядке: удаление одноимённой cookie
может затронуть локально новую cookie, но сервер закрывает только
сессию из JWT конкретного logout. Для однозначного UX клиент должен
сериализовать login/logout; глобальный выход из других сессий не обещается.

## 7. Защита cookie и CSRF

1. Удалять только `session_token`, с `Path=/`, без `Domain`, то есть
   в том же host-only scope, в котором login установил cookie.
2. Set-Cookie удаления должен содержать пустое значение, `Max-Age=0`,
   истёкший `Expires`, `Secure`, `HttpOnly`, `SameSite=Lax`.
   Атрибуты защиты задаются явно и при удалении.
3. Рабочий транспорт — HTTPS. JavaScript не читает JWT и не удаляет
   HttpOnly cookie вручную. Ответ и ошибки не раскрывают JWT/secret/hash;
   Cookie и Set-Cookie исключаются из прикладного логирования.
4. Logout выполняется только POST. `SameSite=Lax` — дополнительный
   барьер, но не единственная защита: same-site и same-origin различаются.
5. Обязательный `X-AnimeMap-Logout: 1` не позволяет обычной внешней
   HTML-форме выполнить logout. Для cross-origin fetch он вызывает
   CORS preflight; разрешены только явно доверенные origin, POST,
   этот заголовок и credentials. Запрещены wildcard и динамическое
   отражение произвольного Origin для credentialed-доступа.
6. Прокси должен передавать заголовок клиента, не добавлять его
   автоматически к любому входящему запросу, иначе CSRF-барьер исчезает.
   Preflight/OPTIONS не аутентифицирует пользователя и не меняет сессии.
7. Для cross-origin вызова клиент использует `credentials: "include"`;
   для same-origin cookie отправляется браузером автоматически.
   Произвольный cross-site frontend при `SameSite=Lax` не считается
   поддерживаемой топологией: V1 ориентирована на same-origin proxy
   либо явно согласованный same-site deployment.

Заголовок CSRF и параметры CORS — новые предложения backend V1,
подлежащие совместному согласованию; текущий код их не реализует.

## 8. Архитектурные требования к будущей реализации

- Domain: команда закрытия и её инварианты, существующие repository/port
  контракты, общие исключения без HTTP-зависимостей.
- Application: конкретный `LogoutUseCase(BaseUseCase)` с именованным
  методом `logout`, зависимостями через конструктор; сценарий работает
  с токеном и сущностями, не с Request/Response или глобальным config.
- Infrastructure: существующие JWT/Argon2id адаптеры и PostgreSQL
  репозитории; явный async I/O, ORM-маппинг и блокировки.
- Presentation: извлечение cookie без вызова стандартного auth,
  CSRF-проверка, `LogoutUseCaseDI`, ответ без тела и cookie-заголовки.
  Пустому `204` не нужна искусственная Pydantic Response-схема.
- Ошибки переводятся общим `presentation/setup_exceptions.py`.
  Для logout-ошибок требования к no-store и удалению cookie на `401`
  должны применяться к фактическому ответу mapper, а не к отброшенному
  объекту Response ручки. Ошибки commit тоже учитываются.
- При реализации после согласования обновить OpenAPI,
  `docs/endpoints/auth.md`, `docs/auth.md` и документацию SessionEntity.
  Именование, DI и Python-кодстайл — по `agent-rules/`.

## 9. Критерии приёмки

Критерии предназначены для будущей реализации и проверки после
согласования. На этапе подготовки V1 код и тесты не создаются.

| ID | Сценарий и проверяемый результат |
| --- | --- |
| AC-01 | Действительный JWT активного владельца + CSRF-заголовок → `204`, нулевое тело, no-store и корректное удаление cookie |
| AC-02 | После `204` в БД заполнен `closed_at`; остальные поля сессии, включая `secret_hash`, `last_used_at`, `expires_at`, не изменились |
| AC-03 | Повторное предъявление сохранённой копии JWT на `/v1/account/me` даёт `401`; остальные сессии пользователя остаются работоспособны |
| AC-04 | Повторный logout со старым JWT → `401/session_closed` и удаление cookie; исходный `closed_at` неизменен |
| AC-05 | Отсутствующая/пустая cookie → `401/missing_session_cookie`; корректный Bearer без cookie не аутентифицирует |
| AC-06 | Истёкшая сессия, в том числе `now == expires_at`, → `401/session_expired`, удаление cookie, отсутствие записи/продления в БД |
| AC-07 | Поддельная подпись, запрещённый алгоритм, неверные claims/UUID, неверный secret, отсутствующая сессия и неактивный владелец дают соответствующий `401`, не меняя БД |
| AC-08 | Проверки AC-01…AC-07 выполняются с обязательным CSRF-заголовком; без него или при неверном значении → `403`, без cookie-заголовка удаления и без изменения БД |
| AC-09 | GET logout → `405`, внешняя HTML-форма не выполняет выход; недоверенный origin не получает разрешение CORS на credentialed-запрос с CSRF-заголовком |
| AC-10 | Два конкурентных logout дают один `204` и один `401`; закрытие не дублируется, время не меняется |
| AC-11 | Гонки auth/logout проверены на реальном PostgreSQL в обоих порядках: закрытие не теряется, последующего продления после закрытия нет |
| AC-12 | Истечение во время verify/блокировки выявляется финальной проверкой; сессия не закрывается как действительная и не возобновляется |
| AC-13 | Сбой чтения/update/flush/commit не возвращает `204`, не удаляет cookie; незавершённые изменения откатываются. Потеря подтверждения commit отражается как ошибка с неопределённым результатом |
| AC-14 | Commit реально завершён до отправки `204` и Set-Cookie; отдельный auth commit и продление не вызываются |
| AC-15 | Потеря успешного ответа допускает безопасный повтор: сервер не открывает сессию, повторный `401` очищает cookie |
| AC-16 | Доменный close идемпотентен, сохраняет immutable поля и `closed_at >= last_used_at`, включая обратный сдвиг часов |
| AC-17 | В HTTPS-браузере удаляется исходная host-only HttpOnly cookie с Path=/; прокси передаёт Set-Cookie, JS не получает токен |
| AC-18 | Ошибки имеют общий формат; no-store и cookie-политика соблюдены на реальных ответах mapper, включая ошибки завершения транзакции; секреты отсутствуют в ответах и логах |
| AC-19 | Выход доступен user/moderator/admin на одинаковых условиях; нельзя передать ID другой сессии вместо JWT и закрыть её |

Проверки доменных инвариантов — unit; HTTP/ошибки/cookie — API;
сериализация, commit и rollback — integration с реальным PostgreSQL;
доставка HttpOnly cookie, CORS и проксирование — браузерная/сквозная проверка.

## 10. Пункты совместного согласования

Перед разрешением реализации обе команды должны явно согласовать:

1. `POST /v1/auth/logout`, пустой запрос и `204` без JSON/редиректа.
2. Сохранение существующего `401` для отсутствующей, закрытой и истёкшей
   сессии; трактовку `204` и `401` как завершения локального входа.
3. Удаление cookie на `204/401` и её сохранение на `403` и сбоях;
   отсутствие ложного подтверждения при сетевой ошибке.
4. Обязательный `X-AnimeMap-Logout: 1`, передачу заголовка и Set-Cookie
   через proxy, фактические доверенные origin и HTTPS-топологию.
5. Сериализацию клиентских login/logout и границы гарантий для
   уже аутентифицированных параллельных запросов.

До совместного согласования этот документ остаётся независимой
backend-спецификацией V1. Создание документа не разрешает реализацию
и не меняет действующий код или утверждённые контракты проекта.
