# Аутентификация и авторизация MVP

## Модель

- Пользователь входит по идентификатору и текущему паролю из [`Credential`](entities/credential.md).
- Успешный вход создаёт [`SessionEntity`](entities/session.md) и устанавливает **один JWT в Secure HttpOnly cookie**. Нет отдельных access/refresh-токенов, refresh endpoint или ротации при обычном использовании.
- Время действительности токена совпадает со временем действительности сессии. Срок скользящий: успешная аутентификация продлевает его на интервал неактивности.
- Авторизация после аутентификации выполняется через RBAC по текущей роли пользователя из БД; матрица прав — в [`User`](entities/user.md).

## JWT

Минимальный payload:

```json
{
  "jti": "<UUIDv4 сессии>",
  "secret": "<случайный секрет сессии>",
  "iat": 1793145600
}
```

- `jti` — строковое представление `sessions.id`.
- `secret` — секрет конкретной сессии, проверяемый по `sessions.secret_hash`.
- `iat` — время выпуска в формате NumericDate.
- JWT подписывается EdDSA (Ed25519), алгоритм жёстко задан адаптером. Ключ подписи не совпадает с `sessions.secret`; `JWT_PRIVATE_KEY` содержит base64 PEM приватного ключа. Настройки и порты — в [security.md](security.md).
- В MVP `exp` не включается: фиксированное значение стало бы противоречить скользящему сроку без перевыпуска JWT. Это обязательный контракт JWT-валидатора для данного сценария. Актуальные `closed_at` и `expires_at` проверяются в БД **при каждом использовании**, одной проверки подписи недостаточно.
- JWT остаётся тем же после продления. Абсолютного предельного срока сверх интервала неактивности сейчас нет.
- Роль, активность пользователя и полномочия не берутся из JWT: изменения в БД учитываются при очередной проверке запроса.

## Хранение и передача клиентом

Сервер устанавливает JWT в cookie при успешном входе:

```http
Set-Cookie: session_token=<jwt>; HttpOnly; Secure; SameSite=Lax; Path=/
```

Браузер автоматически прикладывает cookie к подходящим HTTPS-запросам. JavaScript не читает токен и не формирует `Authorization`. API извлекает JWT только из `session_token`; наличие bearer-заголовка без cookie не аутентифицирует запрос. Токен не возвращается в JSON.

Cookie не имеет `Domain`, `Expires` или `Max-Age`: это браузерная session cookie, а актуальный срок аутентификации хранится в БД. При продлении сессии не требуется переустанавливать неизменный JWT или обновлять фиксированный срок cookie. Закрытие браузера может завершить хранение cookie раньше серверного срока. Для cross-origin-запросов клиент должен включать отправку credentials; конфигурация CORS будет определяться при подключении клиента.

## Вход

Первая миграция создаёт bootstrap-аккаунт `root` с начальным паролем `root`, email `root@example.com` и ролью `admin`. Его пароль проверяется обычным Argon2id verify по текущему credential; отдельного обхода аутентификации для root нет. В presentation вход выполняется по email, поскольку username пока не уникален.

1. Получить email и пароль через Pydantic-схему. Email нормализуется через `trim + lowercase`; пароль передаётся без изменения пробелов.
2. Найти пользователя и убедиться, что он активен.
3. Получить единственный текущий credential и проверить пароль по его Argon2id-хэшу. Исторические пароли не подходят для входа.
4. Создать UUIDv4 сессии и случайный секрет. Рассчитать Argon2id-хэш секрета с индивидуальной солью.
5. Установить `created_at = last_used_at = now`, `closed_at = NULL`, `expires_at = now + timedelta(minutes=app_config.session_idle_timeout_minutes)`.
6. Сохранить сессию, содержащую секрет и его хэш, и подписать JWT с её ID и секретом. Установить cookie только после успешного сохранения сессии.
7. Браузер сохраняет HttpOnly cookie из `Set-Cookie` и автоматически отправляет её в последующих запросах.

## HTTP-контракты входа и регистрации

Существующий префикс API — `/v1`; auth-роутер имеет префикс `/auth`. Запросы принимаются как JSON.

### POST /v1/auth/login

Схемы: `api/schemas/requests/login.py` (`LoginRequest`) и `api/schemas/responses/login.py` (`LoginResponse`). Это внешние Request/Response-объекты, а не внутренние DTO. Схема ответа выводится FastAPI из возвращаемого типа без `response_model`.

```json
{
  "email": "root@example.com",
  "password": "root"
}
```

После успешного входа ответ `200 OK` устанавливает cookie и содержит пустой JSON-объект:

```json
{}
```

Ответ имеет `Cache-Control: no-store`. Срок сессии остаётся в SessionEntity и не передаётся клиенту. Сам JWT передаётся исключительно через `Set-Cookie`.

### POST /v1/auth/register

Схема: `api/schemas/requests/register.py` (`RegisterRequest`). У редиректа нет JSON-тела, поэтому отдельной схемы Response нет.

```json
{
  "email": "anime-fan@example.com",
  "username": "anime-fan",
  "password": "user password",
  "display_name": "Anime Fan"
}
```

- Email обязателен, не длиннее 254 символов, нормализуется через `trim + lowercase`, затем проверяется встроенным `pydantic.EmailStr`. Уникальность обеспечивает БД, RegisterUseCase переводит конфликт в `409`. Bootstrap email — `root@example.com`.
- Username обязателен, после удаления пробелов по краям имеет длину 1–100 символов. Уникальность не вводится.
- Display name необязателен (`null` или отсутствие поля); при наличии после trim имеет длину 1–100 символов.
- Пароль — непустая строка. Он не нормализуется и хранится в Pydantic-схеме как `SecretStr`. Дополнительная политика сложности пока не вводится, в том числе для совместимости с bootstrap-паролем.
- Неизвестные поля запрещены. Клиент не передаёт `role`, `is_active`, ID, хэши или временные метки; RegisterUseCase создаёт роль `user`.

После успешного завершения регистрации возвращается `303 See Other` с `Location`, полученным через именованный login-маршрут (например, `http://localhost:8080/v1/auth/login`). Тела JSON и токена нет; автоматический вход не выполняется. При ошибке регистрации редиректа нет.

Это REST-контракт, страницы логина в бэкенде нет: клиент обрабатывает `303/Location` как переход к шагу входа и после ввода данных отправляет отдельный `POST /v1/auth/login`. Автоматическое HTTP-следование редиректу выполняет GET, тогда как login поддерживает только POST; для API-клиента следует отключить автоматическое следование.

### Ошибки и подключение сценариев

- `400` — ошибка Pydantic-валидации запроса.
- `401` — неверные данные входа, неактивный пользователь, отсутствие cookie или недействительная сессия.
- `409` — контракт конфликта при регистрации уже занятого email.
- `503` — недоступность инфраструктуры.

Presentation преобразует `LoginRequest`/`RegisterRequest` в application `LoginDTO`/`RegisterDTO` через методы `to_dto()` самих Request-моделей. Функции `get_login_usecase` и `get_register_usecase` собирают экземпляры, а алиасы `LoginUseCaseDI`/`RegisterUseCaseDI` оформлены через `Annotated[UseCase, Depends(provider)]`. В аннотации endpoint используется `use_case: LoginUseCaseDI`, внутри вызывается `use_case.login(data.to_dto())` или `use_case.register(data.to_dto())`. UseCase не callable.

Результат `LoginResultDTO` содержит только JWT; endpoint устанавливает cookie и формирует пустой `LoginResponse` через classmethod `LoginResponse.from_dto(result)`. Маппинг в Response не раскрывает токен в JSON. Срок сессии не покидает модель сессии. Application DTO — dataclasses с `slots=True, kw_only=True`, без зависимостей от Pydantic/FastAPI. Внешние Request/Response не имеют суффикса DTO.

LoginUseCase, RegisterUseCase и AuthUseCase реализованы через доменные репозитории, JwtProviderPort и SecretManagerPort. Presentation отвечает за cookie и HTTP-маппинг. API-тесты проверяют контракты без БД; интеграционные тесты проверяют регистрацию, вход и защищённые запросы с реальными PostgreSQL, EdDSA и Argon2id.

Собственные ошибки во всех слоях — общие доменные исключения, наследники `BaseDomainException`; операция, сущность и причина задаются через `details`. Mapper presentation возвращает единый `error/message/details`; полный [контракт ошибок](errors.md).

`AuthUseCase` — исключение в порядке DI: обёртка `get_authenticated_user` читает cookie через `APIKeyCookie`, вызывает `use_case.authenticate(token)` и возвращает `UserDTO`. Алиас `AuthUseCaseDI = Annotated[UserDTO, Depends(get_authenticated_user)]` используется в защищённой ручке как `user: AuthUseCaseDI`. Сам UseCase собирается функцией `get_auth_usecase`. Application AuthUseCase принимает строку токена, не cookie/request; схема cookie-аутентификации отражается в OpenAPI как `in: cookie`.

Обёртка текущего пользователя расположена в `api/di/entities/user.py`; фабрика AuthUseCase — в `api/di/auth.py`. Login/register используют общую PostgresSessionDI, auth — отдельную AuthPostgresSessionDI с фиксацией продления до возврата пользователя. Правила ORM-маппинга, flush и владения транзакцией — в [документации репозиториев](repositories.md).

## Проверка каждого запроса

1. DI-обёртка извлекает JWT из `session_token` cookie. Отсутствующий или некорректный токен на защищённом endpoint отклоняется. Передать токен в AuthUseCase.
2. Проверить подпись разрешённым алгоритмом, структуру payload, типы полей и UUID в `jti`.
3. Найти сессию по `jti` и её владельца. Отклонить запрос, если сессия отсутствует, закрыта, истекла или пользователь неактивен.
4. Проверить `secret` из JWT через Argon2id verify относительно `secret_hash`. Открытое поле `sessions.secret` не подменяет verify.
5. Перед записью повторно проверить состояние сессии и активность владельца, взять актуальное серверное время. Атомарно обновить `last_used_at` и `expires_at` по правилу скользящего срока. Не допустить возобновления после конкурентного закрытия или истечения.
6. После успешного сохранения обновления сформировать аутентифицированного пользователя с его текущей ролью.
7. Вернуть пользователя через auth DI и проверить разрешение на операцию и, где необходимо, владение ресурсом. Недостаток прав даёт `403`; ошибка аутентификации — `401`.

Успешная аутентификация считается использованием сессии даже при последующем `403` или ошибке бизнес-операции. Продление фиксируется отдельно от транзакции бизнес-сценария, чтобы её откат не отменял использование. Ошибочные токены и неуспешный verify срок не продлевают. При недоступности хранилища успешная аутентификация не подтверждается; инфраструктурная ошибка не маскируется под неверный пароль.

Для параллельных запросов обновление времён не должно двигать `last_used_at` назад. Закрытие и продление используют согласованный порядок блокировок либо условное обновление с проверкой числа изменённых строк. После закрытия ни один последующий запрос не может продлить сессию; уже аутентифицированный запрос не отменяется задним числом.

## Выход и истечение

- Выход закрывает текущую сессию установкой `closed_at` и удаляет cookie серверным `Set-Cookie` с теми же именем и Path. JavaScript не удаляет HttpOnly cookie напрямую. Удаление cookie без закрытия записи не является серверным выходом.
- Истечение проверяется по `now >= expires_at` независимо от наличия `closed_at`. Обновить истёкшую сессию обычным запросом нельзя — нужен повторный вход.
- Повторное закрытие на уровне модели идемпотентно. Повторный HTTP-запрос с уже недействительным JWT в cookie проходит обычные правила отказа в аутентификации.
- Автоматическое закрытие остальных сессий при смене или сбросе пароля пока не определено.

## Хэширование и границы слоёв

- Пароли и секреты сессий хэшируются **Argon2id** с индивидуальной солью. В БД хранится полная кодированная строка хэша с параметрами. Настраиваемые начальные параметры закреплены в [security.md](security.md).
- Хэширование и verify выполняются вне асинхронного event loop через соответствующий инфраструктурный адаптер. JWT-подпись и Argon2id — разные операции: одна не заменяет другую.
- Domain содержит сущности, общие исключения, репозиторные интерфейсы и порты внешних интеграций. Application не содержит портов: UseCase координируют вход, проверку, продление, выход и RBAC через доменные репозитории и порты. Операции с сущностями, включая поиск, относятся к репозиториям.
- Infrastructure реализует хэширование, JWT, репозитории и атомарные изменения БД. Presentation отвечает за Pydantic DTO, cookie, DI и HTTP-ответы.
