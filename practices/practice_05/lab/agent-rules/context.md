# Контекст проекта AnimeMap API

## Назначение документа

Этот файл хранит общий контекст всего проекта: назначение продукта, согласованные бизнес-требования, архитектуру, ограничения и правила совместной разработки. Он не ограничивается контекстом отдельного слоя или задачи.

Правила суффиксов типов, размещения схем и DI закреплены в `agent-rules/naming.md` и обязательны при разработке.

Перед выполнением каждой команды или задачи агент должен проверять содержимое `agent-rules/`, читать актуальные правила и соблюдать описанные в них принципы. При изменении договорённостей контекст необходимо актуализировать.

## Продукт и границы MVP

**AnimeMap API** — бэкенд-сервис для поиска реальных локаций из аниме и получения их географических координат. MVP включает поиск, выдачу координат, верификацию координат и пользовательское избранное.

Основной интерфейс сервиса — REST API с JSON. Приоритет производительности — низкая задержка ответов для мобильных клиентов, в том числе за счёт кэширования частых запросов.

### Основные бизнес-требования

1. Пользователь может искать локации по тайтлу аниме, названию локации и тегам.
2. Результат поиска — список локаций с координатами и статусом верификации.
3. Пользователь может отдельно запросить координаты конкретной локации.
4. Сервис должен поддерживать верификацию координат и хранение данных модерации. Конкретные статусы и процесс модерации пока не определены.
5. Пользователь может управлять своим избранным. Добавление локации в избранное возвращает подтверждение операции; точный состав остальных операций и их контрактов предстоит согласовать.
6. Данные локаций, пользователей, избранного и модерации хранятся в PostgreSQL.
7. Часто повторяющиеся запросы координат и результаты поиска кэшируются в Redis.
8. Для геокодинга используются внешние API через `httpx`. OpenStreetMap/Nominatim — возможный провайдер, а не окончательно закреплённая интеграция.

### Входы и результаты API

| Сценарий | Вход | Результат |
| --- | --- | --- |
| Поиск локаций | Критерии поиска: тайтл, название, теги | Список локаций с координатами и статусом верификации |
| Получение координат | Запрос координат конкретной локации | Координаты локации |
| Управление избранным | Операция над избранным пользователя | Для добавления — подтверждение добавления |

Конкретные URL, HTTP-методы, поля запросов и ответов, пагинация и форматы ошибок пока не согласованы.

## Технологический стек

| Область | Решение |
| --- | --- |
| Язык и HTTP-фреймворк | Python + FastAPI |
| Основное хранилище | PostgreSQL |

## Архитектурные принципы

Бэкенд строится на **гексагональной архитектуре, DDD, ООП и SOLID**. Архитектуру и шаблоны задаёт человек; агент развивает реализацию в соответствии с ними.

### Слои и ответственность

- **Domain** — предметная модель и бизнес-правила: сущности, value objects, перечисления, доменные исключения, порты и контракты репозиториев.
- **Application** — прикладные сценарии (`usecases`) и DTO; координация выполнения сценариев через доменную модель и абстракции.
- **Infrastructure** — адаптеры PostgreSQL/SQLAlchemy, Redis и внешних API; ORM-модели и преобразования между ORM-моделями и доменными сущностями.
- **Presentation** — HTTP-интерфейс FastAPI, Pydantic-схемы запросов и ответов, маршрутизация и представление ошибок.
- **Config / bootstrap** — конфигурация и сборка приложения, связывание конкретных адаптеров с прикладными сценариями.

Зависимости направлены к ядру: domain не зависит от FastAPI, Pydantic-схем API, SQLAlchemy, Redis или HTTP-клиента. Application работает с доменной моделью и контрактами, а конкретные инфраструктурные реализации подключаются при сборке приложения. Бизнес-правила не размещаются в HTTP-обработчиках или ORM-моделях.

UseCase — конкретная единица работы application, а не абстрактный класс. Все интерфейсы зависимостей и необходимые настройки передаются в его конструктор извне; DI собирает конкретные реализации. UseCase не создаёт адаптеры самостоятельно и не читает глобальную конфигурацию. Подробные правила — в `agent-rules/naming.md`.

В application нет портов: интерфейсы внешних интеграций находятся в domain. Любые операции с сущностями, включая поиск, реализуются через доменные репозитории (`domain/repositories/`), возвращающие доменные сущности. По умолчанию application содержит DTO и UseCase; application service с CRUD-логикой вокруг сложной сущности допускается только по прямому указанию пользователя.

Во всех слоях используются общие доменные ошибки из `domain/exceptions/entities/`, наследующие `BaseDomainException`. Контекст передаётся через `details`, не через имя класса. Единый mapper `presentation/setup_exceptions.py` переводит их в HTTP-ответы `error/message/details`; ошибки валидации запроса возвращают `400`. Подробный контракт — в `docs/errors.md`.

Все UseCase наследуются от `BaseUseCase`. Минимальное разрешение задаётся через `super().__init__(min_permission=...)`, по умолчанию `UserRole.USER`, и хранится в `access_level`. Метод `authorize(user)` возвращает результат `self.access_level <= user.role`. Иерархия ролей: USER (1) < MODERATOR (2) < ADMIN (3). Публичные вход и регистрация не требуют предварительной авторизации; проверка активности и владения ресурсами выполняется отдельно.

### Модели, DTO и идентификаторы

- Строгая типизация обязательна для моделей, DTO и ответов API.
- В presentation используются внешние Pydantic-схемы `Request`/`Response` без постфикса DTO. DTO — внутренние объекты приложения, не прямые входы и выходы HTTP-ручек.
- Маппинг presentation → application реализуется в `Request.to_dto()`, обратный маппинг — в `Response.from_dto(cls, dto)` как classmethod. Ручки используют эти методы вместо ручного маппинга полей.
- GET Request-модели подключаются через `Annotated[Model, Query()]`. Общий `PaginationRequest` задаёт `limit=20` (1–100) и `offset=0` (0–10 000); все Request с пагинацией наследуются от него. При отсутствии других query-полей, в том числе в account/find, используется сам PaginationRequest. Его `to_dto()` формирует PaginationDTO, а границы страницы передаются через UseCase в репозиторий.
- Все dataclasses имеют `kw_only=True`. В domain и application для моделей данных и DTO также обязателен `slots=True`. Это требование не означает, что каждый сервис или use case должен быть dataclass.
- В infrastructure используются отдельные ORM-модели SQLAlchemy с явным маппингом в доменные сущности и обратно.
- Каждая ORM-модель находится в отдельном файле. Используются `from __future__ import annotations`, `Mapped`/`mapped_column` и `relationship`; импорты связанных моделей для аннотаций помещаются под `TYPE_CHECKING`. Все модели регистрируются через `models/__init__.py`.
- ORM-модели не подменяют доменные сущности или публичные схемы API.
- Первичные ключи сущностей — UUIDv4.
- Идентификатор создаётся в domain при создании сущности: для получения ID не требуется сохранение в БД или вызов `flush()`.

### Перечисления (enum)

- Все enum внутри приложения, включая domain/application, имеют целочисленные значения; при хранении в БД используется `integer`, а не строковый PostgreSQL enum.
- В presentation значения enum представляются строками. Числовые коды не являются публичным представлением enum в API.
- Преобразование между внутренним enum и строкой API выполняется явно в обе стороны. Для общего механизма допускается базовый класс доменных `IntEnum` с маппингом строковых значений без зависимостей от FastAPI/Pydantic.
- Числовые коды задаются явно, не перенумеровываются и не переиспользуются. Неизвестные коды или строки отклоняются.
- Стандартный `str(IntEnum)` не заменяет согласованный строковый контракт API.

### Пользователи и RBAC

- Для авторизации используется RBAC. У пользователя одна текущая роль, хранящаяся в `users.role` как `integer` и представленная в domain через `UserRole`.
- Описание пользователя, его атрибутов, инвариантов, ролей и матрицы прав хранится в `docs/entities/user.md`.
- `username` пользователя обязателен; подробные правила поля фиксируются в документации `User`.
- Хэши паролей выделены в сущность `Credential`, связанную с пользователем отношением многие-к-одному. Текущий пароль может быть только один. Документация и инварианты — в `docs/entities/credential.md`.
- Первая миграция создаёт bootstrap-аккаунт `root` с начальным паролем `root` и ролью `admin`. Пароль хранится как Argon2id-хэш в текущем credential; повторный запуск не сбрасывает аккаунт. Подробности — в документации `User`.

### Сессии и аутентификация MVP

- Используется один JWT на сессию, без access/refresh-пары и операций refresh. JWT содержит ID сессии (`jti`) и индивидуальный секрет.
- Сервер устанавливает токен в `session_token` cookie с `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`. Браузер автоматически прикладывает cookie; API не извлекает токен из `Authorization` и не возвращает JWT в JSON.
- Действительность JWT определяется состоянием сессии в БД. Срок скользящий: `expires_at = last_used_at + timedelta(minutes=app_config.session_idle_timeout_minutes)`; настройка — положительное целое число минут.
- При успешной аутентификации срок продлевается без изменения JWT. Фиксированный `exp` не включается; проверка сессии обязательна при каждом использовании. Закрытые и истёкшие сессии не возобновляются.
- Для паролей и секретов сессий используется тяжёлое хэширование Argon2id. В сессии для MVP хранятся и секрет, и его хэш; ключ подписи JWT — отдельный серверный ключ.
- Инварианты Session — в `docs/entities/session.md`; процесс аутентификации и RBAC — в `docs/auth.md`.
- После MVP таблица сессий предположительно станет основой refresh-токенов; этот переход сейчас не реализуется.
- Presentation предоставляет `POST /v1/auth/login` (email + пароль → установка cookie, пустой JSON `{}`) и `POST /v1/auth/register` (регистрация → `303` на именованный login-маршрут без автоматического входа). Срок сессии не возвращается клиенту. Схемы находятся в `api/schemas/requests/` и `api/schemas/responses/`.
- Вход выполняется по email: username пока не уникален. Пароль передаётся без нормализации; клиент не задаёт роль и серверные поля регистрации. Подробный HTTP-контракт и правила обработки редиректа — в `docs/auth.md`.
- `GET /v1/account/me` возвращает текущий аккаунт для любого активного аутентифицированного пользователя. `GET /v1/account/find/{username_prefix}` предназначен для moderator/admin; admin наследует права moderator. Поиск ограничен буквальным префиксом username; правила запроса и ответа — в `docs/endpoints/account.md`.
- Для каждого UseCase создаётся отдельная DI в `api/di/`: функция `get_<name>_usecase` возвращает экземпляр, а `<Name>UseCaseDI = Annotated[UseCase, Depends(get_<name>_usecase)]` используется в аннотации ручки. UseCase не callable; presentation вызывает именованный метод (`login`, `register` и т. п.). Исключение — auth: `get_authenticated_user` читает cookie, вызывает `AuthUseCase.authenticate` и возвращает пользователя через алиас `AuthUseCaseDI`. Подробные правила — в `naming.md`.

### Размещение схемы и документации сущностей

- `docs/database.dbml` содержит только схему БД: таблицы, поля, типы, ключи, связи, индексы, значения по умолчанию и ограничения.
- Комментарии и примечания в DBML допускаются только для технических деталей хранения, например поведения `ON DELETE` или обновления временных меток.
- Частичные индексы описываются в блоке `indexes` с соответствующими полями, признаком `unique` при необходимости и `note: 'Partial index: WHERE ...'`. Предикат из примечания должен явно переноситься в миграцию, поскольку DBML не применяет его как SQL-условие.
- Документация сущностей, бизнес-смысл полей, инварианты, роли и права описываются в отдельных Markdown-файлах в `docs/entities/`.
- При добавлении или изменении ручек обязательно обновлять `docs/endpoints/`. Один Markdown-файл описывает группу ручек (`auth.md`, `account.md`), а не отдельный endpoint. Для каждой ручки указывать назначение, кто может ей пользоваться, входы, ответы, ошибки и дополнительную информацию.
- Общие правила проекта остаются в `agent-rules/context.md`; подробности конкретных сущностей указываются ссылками на их документацию.

### Кэширование и внешние интеграции

- Redis используется для кэширования частых запросов координат и результатов поиска.
- При проектировании этих сценариев учитывается приоритет мобильной латентности.
- Работа с Redis и геокодингом инкапсулируется в инфраструктурных адаптерах за соответствующими портами.
- TTL, ключи и инвалидация кэша, поведение при недоступности Redis, таймауты и повторы внешних запросов пока не согласованы.

## Текущий каркас кода

На момент первичного осмотра в `backend/app/` существуют следующие каталоги:

```text
app/
├── domain/
│   ├── entities/
│   ├── enums/
│   ├── exceptions/
│   ├── ports/
│   ├── repositories/
│   └── value_objects/
├── application/
│   ├── dto/
│   └── usecases/
├── infrastructure/
│   ├── cache/
│   └── database/
├── presentation/
│   └── api/routes/
└── config/
```

Также присутствуют `backend/run.py`, каталог миграций Alembic, `pyproject.toml`, `uv.lock`, Dockerfile для сервиса, миграций и тестов, а также заготовки Docker Compose.

Это исходный каркас, а не готовая реализация MVP. В нём есть заготовки асинхронных подключений к PostgreSQL и Redis, базовая ORM-модель и точка входа FastAPI. В `run.py` осталось шаблонное название `Evroprom ID` и ссылки на отсутствующие компоненты; эти детали не являются требованиями AnimeMap API. Наличие Docker-файлов и Compose-заготовок не означает готовность развёртывания в Swarm.

## Правила совместной разработки

- Unit-проверки схем БД размещаются в `backend/tests/unit/database/`, по отдельным файлам для моделей и общих правил. Они работают без подключений к PostgreSQL/Redis и без env. Проверки реальной БД размещаются в `backend/tests/integration/database/`.
- Группа зависимостей `tests` должна обеспечивать самостоятельный запуск тестов через `uv run --group tests pytest`.

- Формат работы — vibe-coding: AI пишет код, человек контролирует решения и результат.
- Бэкенд разрабатывается совместно с пользователем с соблюдением предоставленных им архитектуры, шаблонов и правил.
- Перед каждой командой или задачей необходимо проверять актуальное содержимое `agent-rules/` и действовать в соответствии с ним.
- Схемы и проектная документация размещаются в `docs/`; общие договорённости проекта фиксируются в этом файле.
- Текущий этап — бэкенд. Реализация фронтенда и внешних UI-компонентов в этом репозитории запрещена.
- Несогласованные детали не следует выдавать за утверждённые бизнес-правила.

## Решения, которые предстоит согласовать

- Состав сущностей и агрегатов, их поля, связи и доменные инварианты.
- Статусы верификации, процесс модерации и права участников.
- Параметры Argon2id, конфигурация подписи JWT, анонимный доступ и детальные политики административных операций.
- Полный набор операций с избранным и поведение при повторном добавлении.
- Семантика поиска локаций, сочетание фильтров и сортировка.
- API-контракты и обработка ошибок, включая отсутствие координат или результатов.
- Окончательный провайдер геокодинга и правила взаимодействия с ним.
- Политика кэширования и измеримые цели по задержке ответов.
- Детали конфигурации Nginx и развёртывания в Docker Swarm.
